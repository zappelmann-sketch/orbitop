# Release and packaging

How the orbitop packages are built, which rules they follow, and why the remaining lint tags are accepted.

## Build

`bash scripts/build-packages.sh --out DIR --pubkey FILE [--suffix SUFFIX]` builds from `git archive HEAD` in one disposable container per format (`docker run --rm`, the archive read-only, only `DIR` writable): `debian:trixie`, `fedora:latest`, `opensuse/tumbleweed` and `archlinux:latest`.

- `DIR/deb/orbitop_<version>-1_all.deb` and `DIR/deb/orbitop-apt-source_<packaging/keyring.version>_all.deb`
- `DIR/rpm-fedora/` and `DIR/rpm-opensuse/`, each with `orbitop-<version>-1.noarch.rpm` and `orbitop-release-<packaging/keyring.version>-1.noarch.rpm`
- `DIR/arch/orbitop-<version>-1-any.pkg.tar.zst`
- `DIR/lint/`: `<package>.txt` from lintian, `rpm-fedora.txt` and `rpm-opensuse.txt` from rpmlint, `arch-orbitop.txt` from namcap. The script exits non-zero on an `E:` tag; the one accepted exception is under "Lint notes".
- `FILE` is the armored public key of the package source. On the host, before any container starts, the script dearmors it and checks it with `gpg --show-keys` in a fresh, temporary keyring: exactly one `pub`, no `sec` or `ssb`. Otherwise it stops. Each container receives only this checked binary key on stdin, so a second key or a secret key, even under a `PUBLIC KEY BLOCK` header, never reaches it.
- `--suffix check1` builds a check version that is never published (update test in the container matrix, plan K6): Debian `<version>-1+check1`, RPM `Release: 1.check1`, Arch `pkgrel=1.1` (pacman allows only digits and one dot in `pkgrel`).

The builds inside the containers are `packaging/debian/build-inside.sh`, `packaging/rpm/build-inside.sh` (both RPM families) and `packaging/arch/build-inside.sh`; `scripts/build-packages.sh` only checks the input, prepares the archive and starts the containers. `packaging/install-tree.sh DESTDIR` lays out the file tree of the main package; every package format uses it. `packaging/changelog.py` writes the Debian changelog and the RPM `%changelog` from the `<release>` entries of the metainfo, the only source; the repository holds no `debian/changelog` and no `%changelog` entries. The version comes only from `orbitop/__init__.py`: the RPM build passes it as `orbitop_version`, the Arch build writes `pkgver` in front of a copy of the `PKGBUILD`.

Every format compares the packaged helper `/usr/lib/orbitop/killhelper` byte by byte with `orbitop/killhelper.py` and fails if a packaging tool changed it (pkexec runs it as root; its shebang `#!/usr/bin/python3 -I` must stay).

Debian specifics:

- `dh_python3` byte-compiles `/usr/share/orbitop` in `postinst` and removes the byte code in `prerm` (Python Policy 5.3, below). It runs with `--no-shebang-rewrite`: otherwise it turns the helper's `#!/usr/bin/python3 -I` into `#! /usr/bin/python3` and drops `-I`. The build script fails if the packaged helper differs from `orbitop/killhelper.py`.
- `orbitop.sources` has no `Architectures` field. Probe on 2026-11-18 with a signed `file://` copy of the source (`Release` with `Architectures: all`, only `main/binary-all`): Debian 13 (apt 3.0.4), Ubuntu 24.04 (apt 2.8.4) and Ubuntu 26.04 (apt 3.2.1) print the same lines with and without `Architectures: all`, no `W:`, `E:` or `N:`, exit 0, candidate found. The `Release` file of the source must therefore keep `Architectures: all`.
- `orbitop-apt-source` installs three conffiles under `/etc/apt/`, nothing else: `sources.list.d/orbitop.sources` (`Signed-By: /etc/apt/keyrings/orbitop-archive-keyring.pgp`), `keyrings/orbitop-archive-keyring.pgp` (binary) and `preferences.d/orbitop.pref`. Reason (spec 3, "Pflicht"; plan K3): `apt remove orbitop-apt-source` keeps conffiles. A key under `/usr/share/keyrings` would be deleted while the source stays, and every later `apt update` would fail. As conffiles, source, key and pinning stay together after `remove` and all go with `purge`.
- `orbitop.pref` is `Package: *`, `Pin: origin zappelmann-sketch.github.io`, `Pin-Priority: 100`. apt_preferences(5) documents comments only as `Explanation:` lines at the start of a record, so the SPDX header is written that way.
- Probe on 2026-11-18 in `debian:trixie` (apt 3.0.4). The signed source is served under its real host name through a hosts entry and local HTTP, the only change being `https` → `http` in the installed `orbitop.sources`. Results:
  - `apt-cache policy orbitop` shows `100 http://zappelmann-sketch.github.io/orbitop/apt stable/main all Packages`.
  - With the check build as the newer version, `apt-get upgrade` moved orbitop from `0.1.0-1` to `0.1.0-1+check1`.
  - `apt remove orbitop`, then `apt update`: exit 0, no `W:`/`E:`/`N:`.
  - `apt remove orbitop-apt-source`: status `rc`, all three files stay, `apt update` exits 0 without messages and still finds the candidate.
  - `apt purge orbitop-apt-source`: `/etc/apt/keyrings/` and `/etc/apt/preferences.d/` are empty, `sources.list.d/` holds only `debian.sources`, `apt update` exits 0.
- Only binary packages are built (`dpkg-buildpackage -b`); no Debian source package is built or published. That is why `3.0 (native)` goes together with the revision `-1`.
- `orbitop-apt-source` is a source package of its own (`packaging/apt-source/debian/`). Its version, changelog and `SOURCE_DATE_EPOCH` come only from `packaging/keyring.version`, so the same version gives the same bytes, whatever orbitop is built alongside. Its other inputs are the files in `packaging/apt-source/` and the key. `tests/test_packaging_debian.py` pins them per version: a change needs a new `packaging/keyring.version`. Only the toolchain from the `debian:trixie` image and its mirror is not pinned. The main package does not depend on `orbitop-apt-source` (K3).

RPM specifics (Fedora and openSUSE):

- One recipe, `packaging/rpm/orbitop.spec`, for both families; `%if 0%{?suse_version}` chooses the names. Both require `python3 >= 3.12` and `polkit` and suggest `igt-gpu-tools`. Fedora requires `python3-gobject`, `gtk4`, `webkitgtk6.0`, openSUSE the names of `app.PACKAGES["zypper"]` (plan K4; a test keeps both branches equal to `app.PACKAGES`). `orbitop` never requires `orbitop-release` (K3). The release has no `%{?dist}` tag: one package per family serves all its versions (spec 1).
- `rpmbuild` runs with `_buildhost build`, `source_date_epoch_from_changelog`, `clamp_mtime_to_source_date_epoch` and `use_source_date_epoch_as_buildtime`. `rpm -qip` shows `Build Host: build` and the date of the top `%changelog` entry as `Build Date`, never the container's random host name or the build time.
- Byte code is in the package, as the Fedora Python guidelines require (below): `%py_byte_compile` on Fedora, `%py3_compile` on openSUSE, both for `/usr/share/orbitop/orbitop`. Probe on 2026-11-18: after installing, `python3 -v` reports `…/__pycache__/sysfs.cpython-315.pyc matches …/sysfs.py` on Fedora 45 (Python 3.15) and `…/sysfs.cpython-313.pyc matches …` on Tumbleweed (Python 3.13). Fedora writes time-stamp caches with clamped source times; on openSUSE they are checked-hash caches (flags 3), because `rpmbuild` exports `SOURCE_DATE_EPOCH`. In both cases the clamped time stamps do not invalidate them. The caches carry the tag of the build's Python. After a distribution moves to a new Python version, Python ignores them and reads the sources (it cannot write caches into the root-owned directory) until the next orbitop build.
- `%check` runs `desktop-file-validate` and `appstream-util validate-relax --nonet` (Fedora guidelines, below).
- `orbitop-release` (`packaging/rpm/orbitop-release.spec`, plan K3) installs two files and owns `/etc/pki/rpm-gpg` together with the distribution:
  - Fedora: `/etc/yum.repos.d/orbitop.repo` from `packaging/keyring/orbitop-fedora.repo`. openSUSE: `/etc/zypp/repos.d/orbitop.repo` from `packaging/keyring/orbitop-opensuse.repo`. Both are `%config(noreplace)`.
  - Both: the armored key `/etc/pki/rpm-gpg/RPM-GPG-KEY-orbitop`, not `%config`, like the keys of `fedora-gpg-keys` and `rpm-repo-keys-openSUSE`. An update with a renewed key always replaces it.
  - The `.repo` files: `baseurl=https://zappelmann-sketch.github.io/orbitop/rpm/<family>`, `enabled=1`, `gpgcheck=1`, `repo_gpgcheck=1`, `gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-orbitop`, `priority=100`, on openSUSE also `autorefresh=1`. dnf and zypper prefer the repository with the smaller number and use 99 by default (below), so a package of the distribution always wins over one of this source, as with the apt pinning. orbitop itself is only in this source and is updated. Both files set `gpgcheck` and `repo_gpgcheck` explicitly: under dnf5's default `gpgcheck_policy=legacy`, `gpgcheck=1` alone checks only packages.
  - `enabled=1`: the Third Party Repository Policy requires `enabled=0` only for repository definitions that a Fedora edition or spin ships on its media. Here the admin installs `orbitop-release` on purpose, and that is the explicit enabling.
  - Removing `orbitop-release` removes both files. rpm keeps a changed `.repo` as `orbitop.repo.rpmsave`, which neither dnf nor zypper reads (they read `*.repo`), so no source is left without its key.
  - Version, `%changelog` and build date come only from `packaging/keyring.version`, like `orbitop-apt-source`. `tests/test_packaging_rpm.py` pins its inputs (the spec, both `.repo` files, `LICENSE`, the `%changelog`) per version.
  - Reproducible: probe on 2026-11-18 with the throwaway key, built from the same inputs in fresh containers. Fedora 45 (rpm 6.1.0): three builds, all `orbitop-release-2026.11.18-1.noarch.rpm` with sha256 `a268fd38c78d3d71e5c0e514573782b55b9ed1dd98a427962ad5821c52d71a3d`. Tumbleweed (rpm 4.20.1): two builds, both `7d08edf3869a92192fadc5e193955314334550d7784b2a8c50bf1558ca0e286d`. The `orbitop` RPMs were byte-identical too. Only the toolchain of the images and their mirrors is not pinned.
- Install probe on 2026-11-18, local files in disposable containers. On Fedora 45, `dnf install ./*.rpm` exits 0 with "skipped OpenPGP checks for 2 packages from repository: @commandline". On Tumbleweed, `zypper install --allow-unsigned-rpm ./*.rpm` exits 0; `python3 >= 3.12` resolves to `python313`. On both, `orbitop --version` works and `rpm -V` is clean. `zypper lr -p` lists `orbitop` with priority 100 next to `repo-oss` with 99. After `remove`, no path of either package is left, and on openSUSE `/etc/pki/rpm-gpg` is gone too. Signed packages, `repo_gpgcheck` against a served repository and the first key question come with Task 5 and the container matrix.

Arch specifics:

- `packaging/arch/PKGBUILD` with `orbitop.install`, built in `archlinux:latest` by the unprivileged user `builder` (makepkg refuses root), `PACKAGER` the noreply address. `build-inside.sh` puts `pkgver` and `pkgrel` in front of a copy of the `PKGBUILD`. It provides the sources (the archive as `orbitop-<version>.tar`, the binary key `orbitop.gpg`, `orbitop-trusted`) and appends their sums with `makepkg --geninteg`. The `PKGBUILD` does not use `$startdir`, which PKGBUILD(5) calls deprecated.
- `depends=('python>=3.12' python-gobject gtk4 webkitgtk-6.0 glib2 hicolor-icon-theme polkit)`. `glib2` (Gio, GLib) and `hicolor-icon-theme` (the icon) were added because namcap reports them as `E:` "detected and not included" and the Arch package guidelines forbid relying on transitive dependencies (below). `optdepends=('intel-gpu-tools: Intel GPU load of all processes')`. Before `makepkg`, the build installs the `depends` from the repositories as dependencies, so pacman checks every name and namcap sees the packages it analyses.
- `license=('GPL-3.0-or-later' 'OFL-1.1' 'CC0-1.0')`. OFL-1.1 is no common license of Arch; namcap requires its text below `/usr/share/licenses/orbitop/`, so both `OFL-*.txt` are copied there as well.
- Byte code: `python -m compileall` in `package()`, so pacman tracks the caches (Arch Python package guidelines, below). Probe: `python -v` reports `…/__pycache__/sysfs.cpython-314.pyc matches …/sysfs.py`.
- Keyring (pacman-key(8), "Providing a keyring for import"): `/usr/share/pacman/keyrings/orbitop.gpg` (binary) and `orbitop-trusted` with one line `<fingerprint>:4:`. 4 is the owner trust "marginal", as in `archlinux-trusted`. `orbitop.install` runs `pacman-key --populate orbitop` in `post_install` and `post_upgrade`.
- Install probe on 2026-11-18 (`pacman -U` of the local file): pacman prints "Locally signing trusted keys in keyring" and "Importing owner trust values", and the key then has validity `f` and owner trust `m`. `pacman -Qkk orbitop` reports 0 altered files. After `pacman -R orbitop`, no file of the package is left. The key stays in pacman's keyring; the README explains `pacman-key --delete` (spec 3). The docker image ships no local master key. Without `pacman-key --init`, `--populate` fails with "There is no secret key available to sign with", pacman prints "command failed to execute correctly", and the installation still succeeds. A real Arch system creates the master key during installation.

## Sources

Read on 2026-11-18 before building. Quotes are verbatim.

- **Debian Policy 4.7.4.1, 9.1.1 "File System Structure"**, <https://www.debian.org/doc/debian-policy/ch-opersys.html#file-system-structure>:
  "The location of all files and directories must comply with the Filesystem Hierarchy Standard (FHS), version 3.0, with the exceptions noted below". Exception 1: "a subdirectory of /usr/lib may be used by a package (or a collection of packages) to hold a mixture of architecture-independent and architecture-dependent files. However, when a directory is entirely composed of architecture-independent files, it should be located in /usr/share." The policy does not mention `/usr/libexec` itself.
- **FHS 3.0, 4.6 "/usr/lib"**, <https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04s06.html>: "On some systems, it may also include internal binaries that are not intended to be executed directly by users or shell scripts. Applications may use a single subdirectory under /usr/lib." 4.7 "/usr/libexec", <https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04s07.html>: "Applications which use /usr/libexec in this way must not also use /usr/lib to store internal binaries […] Either practice is now acceptable, but each application must choose one way or the other".
  Result for the root helper (K1): `/usr/lib/orbitop/killhelper`. It is an internal program, not a static data file, so the "should be located in /usr/share" sentence above does not apply; orbitop keeps all internal programs in `/usr/lib/orbitop`.
- **Debian Policy 4.7.4.1, 9.1.2 "Site-specific programs"**, same page: "As mandated by the FHS, packages must not place any files in /usr/local, either by putting them in the file system archive to be unpacked by dpkg or by manipulating them in their maintainer scripts." This is why the helper moved away from `/usr/local/libexec/orbitop/`.
- **Debian Policy 4.7.4.1, 10.7.3 "Behavior"**, <https://www.debian.org/doc/debian-policy/ch-files.html#behavior>: "configuration files must be preserved when the package is removed, and only deleted when the package is purged." A conffile's default version "must not be modified by the maintainer scripts during installation (or at any other time)." **10.7.4 "Sharing configuration files"**: "The maintainer scripts must not alter a conffile of any package, including the one the scripts belong to."
  Result (K3): the apt source is a conffile of its own package `orbitop-apt-source`, together with the key it names. Removing `orbitop` leaves both in place, so `apt update` keeps working; purging `orbitop-apt-source` removes both.
- **Debian Python Policy, 5.3 "Programs Shipping Private Modules"**, <https://www.debian.org/doc/packaging-manuals/python-policy/#programs-shipping-private-modules>: "These modules should be installed in /usr/share/module, or /usr/lib/module if the modules are architecture-dependent (e.g. extensions). […] the byte-compiled modules must not be shipped with the binary package, they should be generated in the package's post-install script using the current default Python version, and removed in the pre-remove script."
  Result (K2): the program lives in `/usr/share/orbitop/`; `dh_python3` adds the `py3compile`/`py3clean` calls to `postinst`/`prerm`.
- **Debian Wiki, DebianRepository/UseThirdParty**, <https://wiki.debian.org/DebianRepository/UseThirdParty>: "Certificate updates SHOULD be distributed by a Debian package called deriv-archive-keyring." "This package MUST distribute the certificate in binary form as /usr/share/keyrings/deriv-archive-keyring.pgp" and "MAY also include the /etc/apt/sources.list.d/deriv.sources or /etc/apt/sources.list.d/deriv.list files." "The signed-by entry MUST point to a file, and not a fingerprint." "The certificate MUST NOT be placed in /etc/apt/trusted.gpg.d or loaded by apt-key add."
  On pinning: "a matching preferences file SHOULD be created to restrict the possible effects of the repository." "If such a preferences file is used it MUST pin with a user-controlled label" and "MUST NOT use a field provided by the upstream Release file." "The Pin-Priority field MAY be set so that packages are upgraded by default (Pin-Priority: 100) or not (Pin-Priority: 1)" "but it MUST NOT be set to any higher value that may lead to overwriting packages" "shipped with the default Debian distribution." The keyring package "MAY also include […] the /etc/apt/preferences.d/deriv.pref file", and then "the preferences file MUST allow automatic upgrades (Pin-Priority: 100)". On key locations: "If future updates to the certificate will be managed by an apt/dpkg package as recommended below, then it SHOULD be downloaded into /usr/share/keyrings […]. If it will be managed locally, it SHOULD be downloaded into /etc/apt/keyrings instead."
  Result (K3): one package `orbitop-apt-source` with `/etc/apt/sources.list.d/orbitop.sources` (deb822), the key `/etc/apt/keyrings/orbitop-archive-keyring.pgp` and `/etc/apt/preferences.d/orbitop.pref` (`Pin: origin zappelmann-sketch.github.io`, the host name from the user's own `sources` entry, not a field of the `Release` file; priority 100). The key file keeps the name from this page. The place deviates from this page, which puts a package-managed key under `/usr/share/keyrings` (a MUST for a `deriv-archive-keyring` package, a SHOULD for downloads). The reason: there, `apt remove` would delete the key and keep the source (above, Debian specifics). The controller ruled this on 2026-11-18 (plan K3). The package itself is called `orbitop-apt-source`, because lintian allows a file in `sources.list.d` only in packages named `*-apt-source` (tag `package-installs-apt-sources`: "packages whose names end in the clearly named -apt-source are permitted to install such files").
- **apt_preferences(5)**, apt 3.2.1 (local man page; online <https://manpages.debian.org/trixie/apt/apt_preferences.5.en.html>): "If the target release has not been specified then APT simply assigns priority 100 to all installed package versions and priority 500 to all uninstalled package versions". "100 <= P < 500 causes a version to be installed unless there is a version available belonging to some other distribution or the installed version is more recent". "Install the highest priority version." "If two or more versions have the same priority, install the most recent one (that is, the one with the higher version number)." "the keyword used here is "origin" which can be used to match a hostname." "Each record in the APT preferences file can optionally begin with one or more lines beginning with the word Explanation:. This provides a place for comments."
  Result: at priority 100 a newer orbitop from this origin has the same priority as the installed version, so the higher version wins and `apt upgrade` installs it; a package of the distribution (500) always wins over one of this origin.
- **ArchWiki, Arch package guidelines, "Directories"** (page last edited 2 May 2026; wiki.archlinux.org refused the automated request, so read from package `arch-wiki-docs` 20261101-1 in a disposable `archlinux:latest` container): table rows "/usr/lib/pkg — Modules, plugins, etc." and "/usr/share/pkg — Application data"; "Packages should never be installed to /usr/local/."; "Avoid using /usr/libexec/ for anything.   Result: `/usr/lib/orbitop/` for the helper is the one location every format accepts (K1); `/usr/libexec` would not be.

- **pkexec(1)**, <https://polkit.pages.freedesktop.org/polkit/pkexec.1.html>: "To use another action, use the org.freedesktop.policykit.exec.path annotation on an action with the value set to the full path of the program." VARIABLES: "The following variables are set by pkexec.   Result: pkexec starts `/usr/lib/orbitop/killhelper` directly (its shebang `#!/usr/bin/python3 -I`), so the annotation matches only the helper; the dialog message ends in `$(command_line)`.
- **freedesktop.org, Desktop Application Autostart Specification 0.51**, <https://specifications.freedesktop.org/autostart/latest/>: 2.1 "If the same filename is located under multiple Autostart Directories only the file under the most important directory should be used."   Result (K5): the package ships only the inactive template `/usr/share/orbitop/autostart.desktop` (`TryExec=orbitop`) and never an entry in `/etc/xdg/autostart`.

The rendered pages are at <https://docs.fedoraproject.org/en-US/packaging-guidelines/>.

- **Fedora Packaging Guidelines, "Configuration Files"** (`index.adoc`): "As a rule of thumb, use `%config(noreplace)` instead of plain `%config` unless your best, educated guess is that doing so will break things." "Don't use %config or %config(noreplace) under /usr." **"Configuration of Package Managers"**: "Packages MUST NOT install repository configuration files which violate the Third Party Repository Policy, unless those files are installed under `%{_docdir}`."
  Result: both `.repo` files are `%config(noreplace)`; the key is not configuration.
- **FESCo, Third-Party Repository Policy**, <https://docs.fedoraproject.org/en-US/fesco/Third_Party_Repository_Policy/>: "Third-party repositories should be distributed in descriptively named rpm packages." "Each third-party repository should be defined once through a separate (binary) package." "RPM packages in a third-party repository must not replace packages provided by official Fedora repositories, nor break dependencies between those packages." The policy "sets out the conditions under which Fedora editions and spins can include repository definitions"; for those, "repository files must initially include the enabled=0 (or equivalent) setting, and the user must explicitly enable third-party repositories to install from them."
  Result (K3): the own package `orbitop-release`, `priority=100` so that no Fedora package is replaced, and `enabled=1`, because installing `orbitop-release` is the user's explicit choice and the package is not part of Fedora media.
- **Fedora Packaging Guidelines, "Shebang Lines"**: "Shebang lines for executable scripts are automatically modified to convert calls to `env` into direct use of the proper executable in `/usr/bin`." "It is also possible to disable the functionality for specific paths or for specific shebang lines by setting `%__brp_mangle_shebangs_exclude_from` and `%__brp_mangle_shebangs_exclude`".
  Result: nothing is disabled, because the shebangs already name `/usr/bin/python3` and stay as they are. The build compares the packaged helper with the source and fails on any change.
- **Fedora Packaging Guidelines, "Libexecdir"**: "Fedora packages MAY store appropriate files there." "If upstream's build scripts do not support that, `%{_libdir}/%{name}` is a valid second choice."
  Result (K1): `/usr/lib/orbitop/killhelper` is allowed. For a noarch package that is `%{_prefix}/lib`, the one location that all four formats accept.
- **Fedora Packaging Guidelines, "File and Directory Ownership"**: "Packages must own all directories they put files in, except for: […] any directories owned by other packages in your package's natural dependency chain". "When co-owning directories, you *must* ensure that the ownership and permissions on the directory match in all packages that own it."
  Result: `orbitop-release` co-owns `/etc/pki/rpm-gpg` (root, 0755, as `fedora-gpg-keys` and `rpm-repo-keys-openSUSE`).
- **Fedora Packaging Guidelines, "Desktop Files", "desktop-file-install Usage"**: "one MUST run `desktop-file-install` (in `%install`) OR `desktop-file-validate` (in `%check` or `%install`) and have `BuildRequires: desktop-file-utils`". **AppData** (`AppData.adoc`): "you MUST run `appstream-util validate-relax` (in `%check` or `%install`) and have `BuildRequires: libappstream-glib`".
  Result: `%check` validates both. The spec names the programs (`BuildRequires: /usr/bin/desktop-file-validate`, `/usr/bin/appstream-util`), which resolve on Fedora and openSUSE alike.
- **Fedora Python Packaging Guidelines, "Source files and bytecode cache"** (`Python.adoc`): "Packages *MUST* include the source file (`*.py`) *AND* the bytecode cache (`*.pyc`) for each pure-Python importable module." ## Lint notes

Lintian (Debian trixie) runs with `--display-info --show-overrides` on both `.deb` files in every build. There is no `E:` tag. One tag is overridden, and each remaining `W:` and `I:` tag of `orbitop` is accepted for the reason below.

- `O: orbitop-apt-source: package-installs-apt-preferences [etc/apt/preferences.d/orbitop.pref]`, an error tag overridden in `packaging/apt-source/debian/orbitop-apt-source.lintian-overrides`. This is the only override (test).
  - Lintian flags every file under `etc/apt/preferences.d/`. Its check exempts only the source package `apt`, unlike `package-installs-apt-sources` (`*-apt-source`) and `package-installs-apt-keyring` (`*-apt-source`, `*-archive-keyring`). No package name avoids the tag.
  - DebianRepository/UseThirdParty (above) lets the keyring package "also include […] the /etc/apt/preferences.d/deriv.pref file" and requires that "the preferences file MUST allow automatic upgrades (Pin-Priority: 100)".
  - Without the file, the repository could replace packages of the distribution; the same page says that without it "the user MUST be warned of the security consequences".

- `W: orbitop: initial-upload-closes-no-bugs`: the changelog has one entry with revision 1 and closes no ITP bug. orbitop is not uploaded to Debian (spec, non-goals), so there is no ITP. The tag disappears once the metainfo lists a second release.
- `W: orbitop: no-manual-page [usr/bin/orbitop]`: Debian Policy 12.1 says a program "should" have a manual page. orbitop is a graphical program with two options (`--version`, `--hidden`), described in the README. A manual page is a possible later addition.
- `I: orbitop: font-in-non-font-package` and `I: orbitop: font-outside-font-dir` for `Orbitron.ttf` and `Oxanium.ttf`: the fonts belong to the page in the WebView, which loads them as `orbitop://ui/fonts/…`. The scheme handler serves only `orbitop/ui/`, and system-wide fonts would appear in every font menu.
- `I: orbitop: package-contains-documentation-outside-usr-share-doc` for `ui/index.html`, `ui/fonts/OFL-Orbitron.txt` and `ui/fonts/OFL-Oxanium.txt`: `index.html` is the user interface, not documentation. The OFL texts travel next to their fonts, as the OFL requires, and the app serves them from there; `debian/copyright` carries the license as well.

rpmlint runs once per family over both RPMs: rpmlint 2.9.0 with Fedora's configuration and rpmlint 2.10.0 with openSUSE's. There is no rpmlintrc. The "filtered" counts in the reports come from the distributions' own configurations. The build fails on every `E:` line except the one below, because openSUSE's rpmlint exits 0 below its badness threshold even when it reports an error.

- `E: orbitop: polkit-untracked-privilege (Badness: 10) io.github.zappelmann-sketch.orbitop.terminate (auth_admin:auth_admin:auth_admin)`, openSUSE only. It is the only accepted error, matched as this exact line in `packaging/rpm/build-inside.sh`.
  - openSUSE's rpmlint reports every polkit action that the SUSE security team has not reviewed and listed in `polkit-default-privs`. It asks for that review "if the package is intended for inclusion in any SUSE product"; orbitop is not, it comes from its own package source.
  - `opensuse.toml` puts the tag under `BlockedFilters`, so no rpmlintrc can filter it. That is why the build script accepts the line instead.
  - The line names the action and its defaults: if an action weaker than `auth_admin` appears, the line differs and the build fails.
  - For actions outside its profiles, `polkit-default-privs` adds no rule, so polkit applies the `.policy` defaults `auth_admin` (Sources, above).
- `W: orbitop: only-non-binary-in-usr-lib` (Fedora): `/usr/lib/orbitop/` holds only the helper, a Python script that pkexec starts directly (K1). It is an internal program, not data for `/usr/share`. Fedora's Libexecdir section accepts `%{_libdir}/%{name}`, and `/usr/libexec` is no option for Arch (Sources, above).
- `W: orbitop: no-manual-page-for-binary orbitop` (Fedora): as `no-manual-page` above.
- `W: orbitop: no-documentation` and `W: orbitop-release: no-documentation` (Fedora): both packages carry only their license (`%license`); the README lives in the repository. The Fedora guidelines require no `%doc`.
- `W: orbitop-release: non-conffile-in-etc /etc/pki/rpm-gpg/RPM-GPG-KEY-orbitop` (Fedora and openSUSE): the key is deliberately no `%config`, like `/etc/pki/rpm-gpg/RPM-GPG-KEY-openSUSE` of `rpm-repo-keys-openSUSE`. With `%config(noreplace)`, rpm would keep a changed or old key and save a renewed one only as `.rpmnew`; without it, every update installs the current key.

namcap runs on the `PKGBUILD` and on the package, after the runtime dependencies are installed. There is no `E:` tag (the two missing dependencies and the missing OFL license text were fixed, see "Arch specifics"), the `PKGBUILD` gets no tag, and no tag is filtered. The remaining warnings of the package:

- `W: Referenced python module 'orbitop.…' is an uninstalled dependency` (48 lines, one per imported name such as `orbitop.gpu.GpuReader`): namcap looks for orbitop's own modules in the Python path of the system. They live in the private directory `/usr/share/orbitop/orbitop/` (K2) and are part of this package.
- `W: Referenced library 'python3' is an uninstalled dependency` for `usr/lib/orbitop/killhelper`, `usr/share/orbitop/bin/orbitop` and `usr/share/orbitop/orbitop/killhelper.py`: namcap takes the name `python3` from the shebang `#!/usr/bin/python3` and finds no package of that name. `/usr/bin/python3` belongs to the package `python`, which is in `depends` as `python>=3.12`. The helper's shebang `#!/usr/bin/python3 -I` must stay (K1).
- `W: Dependency included, but may not be needed ('polkit')`: orbitop starts `pkexec` from `polkit` at run time to end foreign processes (`orbitop/actions.py`); namcap cannot see a program that is started by path.
