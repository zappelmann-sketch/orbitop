# Release and packaging

How the orbitop packages are built, which rules they follow, why the remaining lint tags are accepted, how the archive key is kept and how a release runs.

## Build

`bash scripts/build-packages.sh --out DIR --pubkey FILE [--suffix SUFFIX]` builds from `git archive HEAD` in one disposable container per format (`docker run --rm`, the archive read-only, writable only a new, empty directory of its own, never `DIR`): `debian:trixie`, `fedora:latest`, `opensuse/tumbleweed` and `archlinux:latest`. Afterwards that directory may hold only `<format>/` and `lint/` with files. The script moves them to `DIR` and stops on anything else, or on a file that is in `DIR` already, so no image can add, replace or change a package of another format (final security audit, F2).

- `DIR/deb/orbitop_<version>-1_all.deb` and `DIR/deb/orbitop-apt-source_<packaging/keyring.version>_all.deb`
- `DIR/rpm-fedora/` and `DIR/rpm-opensuse/`, each with `orbitop-<version>-1.noarch.rpm` and `orbitop-release-<packaging/keyring.version>-1.noarch.rpm`
- `DIR/arch/orbitop-<version>-1-any.pkg.tar.zst`
- `DIR/lint/`: `<package>.txt` from lintian, `rpm-fedora.txt` and `rpm-opensuse.txt` from rpmlint, `arch-orbitop.txt` from namcap. The script exits non-zero on an `E:` tag; the one accepted exception is under "Lint notes".
- `FILE` is the armored public key of the package source. On the host, before any container starts, the script dearmors it and checks it with `gpg --show-keys` in a fresh, temporary keyring: exactly one `pub`, no `sec` or `ssb`. Otherwise it stops. The key is then imported into that keyring and exported again with `--export-options export-minimal`, the form `build-site.sh` exports and compares byte by byte. Each container receives only this checked binary key on stdin, so a second key or a secret key, even under a `PUBLIC KEY BLOCK` header, never reaches it. All gpg calls run with `--no-options`.
- `--suffix check1` builds a check version that is never published (update test in the container matrix, plan K6): Debian `<version>-1+check1`, RPM `Release: 1.check1`, Arch `pkgrel=1.1` (pacman allows only digits and one dot in `pkgrel`).

The builds inside the containers are `packaging/debian/build-inside.sh`, `packaging/rpm/build-inside.sh` (both RPM families) and `packaging/arch/build-inside.sh`; `scripts/build-packages.sh` only checks the input, prepares the archive and starts the containers. It shares the images, the option parsing, the work directory and the container wrapper with `build-site.sh` in `scripts/container-common.sh`. Every container runs with `--cap-drop MKNOD --cap-drop SETFCAP`; after each one, its directory may hold only regular files and directories without setuid or setgid bits and without file capabilities, or the script stops (Site, "Container output"). Each of them first sources `packaging/container-prologue.sh`, which first refuses to run anywhere but as root in a disposable container (`/.dockerenv`), so that it leaves no file elsewhere, then keeps the key from stdin, checks `OWNER` and hands `/out` to the caller; it also provides `die` and `archive DIR VERSION`. `packaging/install-tree.sh DESTDIR` lays out the file tree of the main package; every package format uses it. `packaging/changelog.py` writes the Debian changelog and the RPM `%changelog` from the `<release>` entries of the metainfo, the only source; the repository holds no `debian/changelog` and no `%changelog` entries. The version comes only from `orbitop/__init__.py`: the RPM build passes it as `orbitop_version`, the Arch build writes `pkgver` in front of a copy of the `PKGBUILD`.

Every format compares the packaged helper `/usr/lib/orbitop/killhelper` byte by byte with `orbitop/killhelper.py` and fails if a packaging tool changed it (pkexec runs it as root; its shebang `#!/usr/bin/python3 -I` must stay).

Debian specifics:

- `dh_python3` byte-compiles `/usr/share/orbitop` in `postinst` and removes the byte code in `prerm` (Python Policy 5.3, below). It runs with `--no-shebang-rewrite`: otherwise it turns the helper's `#!/usr/bin/python3 -I` into `#! /usr/bin/python3` and drops `-I`. The build script fails if the packaged helper differs from `orbitop/killhelper.py`.
- `orbitop.sources` has no `Architectures` field. Probe on 2026-11-18 with a signed `file://` copy of the source (`Release` with `Architectures: all`, only `main/binary-all`): Debian 13 (apt 3.0.4), Ubuntu 24.04 (apt 2.8.4) and Ubuntu 26.04 (apt 3.2.1) print the same lines with and without `Architectures: all`, no `W:`, `E:` or `N:`, exit 0, candidate found. The `Release` file of the source must therefore keep `Architectures: all`.
- `orbitop-apt-source` installs three conffiles under `/etc/apt/`, nothing else: `sources.list.d/orbitop.sources` (`Signed-By: /etc/apt/keyrings/orbitop-archive-keyring.pgp`), `keyrings/orbitop-archive-keyring.pgp` (binary) and `preferences.d/orbitop.pref`. Reason (spec 3, "Pflicht"; plan K3): `apt remove orbitop-apt-source` keeps conffiles. A key under `/usr/share/keyrings` would be deleted while the source stays, and every later `apt update` would fail. As conffiles, source, key and pinning stay together after `remove` and all go with `purge`.
- `orbitop.pref` is `Package: *`, `Pin: origin zappelmann-sketch.github.io`, `Pin-Priority: 100`. apt_preferences(5) documents comments only as `Explanation:` lines at the start of a record, so the SPDX header is written that way.
- Probe on 2026-11-18 in `debian:trixie` (apt 3.0.4). The signed source is served under its real host name through a hosts entry and local HTTP, the only change being `https` → `http` in the installed `orbitop.sources`. Results:
  - `apt-cache policy orbitop` shows `100 http://zappelmann-sketch.github.io/orbitop/apt stable/main all Packages`.
  - With the check build as the newer version, `apt-get upgrade` moved orbitop from `0.1.0-1` to `0.1.0-1+check1`.
  - `apt remove orbitop`, then `apt update`: exit 0, no `W:`/`E:`/`N:`.
  - `apt remove orbitop-apt-source`: status `rc`, all three files stay, `apt update` exits 0 without messages and still finds the candidate.
  - `apt purge orbitop-apt-source`: `/etc/apt/keyrings/` and `/etc/apt/preferences.d/` are empty, `sources.list.d/` holds only `debian.sources`, `apt update` exits 0.
- Only binary packages are built (`dpkg-buildpackage -b`); no Debian source package is built or published. That is why `3.0 (native)` goes together with the revision `-1`.
- `orbitop-apt-source` is a source package of its own (`packaging/apt-source/debian/`). Its version, changelog and `SOURCE_DATE_EPOCH` come only from `packaging/keyring.version`, so the same version gives the same bytes, whatever orbitop is built alongside. Its other inputs are the files in `packaging/apt-source/` and the key. `tests/test_packaging_debian.py` pins them per version, the key as the committed `packaging/keys/orbitop-archive-keyring.asc`, which `release.sh` requires to be, packet for packet, the current export of `ORBITOP_KEY`: a change needs a new `packaging/keyring.version`. Only the toolchain from the `debian:trixie` image and its mirror is not pinned. The main package does not depend on `orbitop-apt-source` (K3).

RPM specifics (Fedora and openSUSE):

- One recipe, `packaging/rpm/orbitop.spec`, for both families; `%if 0%{?suse_version}` chooses the names. Both require `python3 >= 3.12` and `polkit` and suggest `igt-gpu-tools`. openSUSE also requires `/usr/bin/pkexec`: there pkexec is a package of its own (`pkexec`), which `polkit` does not pull in, while Fedora's `polkit` ships the file (probe on 2026-11-20: Fedora 45 `rpm -qf /usr/bin/pkexec` gives `polkit-127`; Tumbleweed has no `/usr/bin/pkexec` after `zypper install polkit`, and zypper resolves the file to `pkexec` 128, not to `run0-wrappers`, which provides it as well). Fedora requires `python3-gobject`, `gtk4`, `webkitgtk6.0`, openSUSE the names of `app.PACKAGES["zypper"]` (plan K4; a test keeps both branches equal to `app.PACKAGES`). `orbitop` never requires `orbitop-release` (K3). The release has no `%{?dist}` tag: one package per family serves all its versions (spec 1).
- `rpmbuild` runs with `_buildhost build`, `source_date_epoch_from_changelog`, `clamp_mtime_to_source_date_epoch` and `use_source_date_epoch_as_buildtime`. `rpm -qip` shows `Build Host: build` and the date of the top `%changelog` entry as `Build Date`, never the container's random host name or the build time.
- Byte code is in the package, as the Fedora Python guidelines require (below): `%py_byte_compile` on Fedora, `%py3_compile` on openSUSE, both for `/usr/share/orbitop/orbitop`. Probe on 2026-11-18: after installing, `python3 -v` reports `…/__pycache__/sysfs.cpython-315.pyc matches …/sysfs.py` on Fedora 45 (Python 3.15) and `…/sysfs.cpython-313.pyc matches …` on Tumbleweed (Python 3.13). Fedora writes time-stamp caches with clamped source times; on openSUSE they are checked-hash caches (flags 3), because `rpmbuild` exports `SOURCE_DATE_EPOCH`. In both cases the clamped time stamps do not invalidate them. The caches carry the tag of the build's Python. After a distribution moves to a new Python version, Python ignores them and reads the sources (it cannot write caches into the root-owned directory) until the next orbitop build.
- `%check` runs `desktop-file-validate` and `appstream-util validate-relax --nonet` (Fedora guidelines, below).
- `orbitop-release` (`packaging/rpm/orbitop-release.spec`, plan K3) installs two files and owns `/etc/pki/rpm-gpg` together with the distribution:
  - Fedora: `/etc/yum.repos.d/orbitop.repo` from `packaging/keyring/orbitop-fedora.repo`. openSUSE: `/etc/zypp/repos.d/orbitop.repo` from `packaging/keyring/orbitop-opensuse.repo`. Both are `%config(noreplace)`.
  - Both: the armored key `/etc/pki/rpm-gpg/RPM-GPG-KEY-orbitop`, not `%config`, like the keys of `fedora-gpg-keys` and `rpm-repo-keys-openSUSE`. An update with a renewed key always replaces it.
  - The `.repo` files: `baseurl=https://zappelmann-sketch.github.io/orbitop/rpm/<family>`, `enabled=1`, `gpgcheck=1`, `repo_gpgcheck=1`, `gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-orbitop`, `priority=100`, on openSUSE also `type=rpm-md`, `autorefresh=1` and `pkg_gpgcheck=1`. dnf and zypper prefer the repository with the smaller number and use 99 by default (below), so a package of the distribution always wins over one of this source, as with the apt pinning. orbitop itself is only in this source and is updated. Both files set `gpgcheck` and `repo_gpgcheck` explicitly: under dnf5's default `gpgcheck_policy=legacy`, `gpgcheck=1` alone checks only packages. zypper accepts packages of a repository with signed metadata by their checksum alone (zypper(8), "GPG checks"), so the openSUSE file adds `pkg_gpgcheck=1`: packages and metadata are both verified (spec 2).
  - `enabled=1`: the Third Party Repository Policy requires `enabled=0` only for repository definitions that a Fedora edition or spin ships on its media. Here the admin installs `orbitop-release` on purpose, and that is the explicit enabling.
  - Removing `orbitop-release` removes both files. rpm keeps a changed `.repo` as `orbitop.repo.rpmsave`, which neither dnf nor zypper reads (they read `*.repo`), so no source is left without its key.
  - The key that dnf or zypper imported into the rpm database on the first update stays there after `remove orbitop orbitop-release`, like every imported key. The full uninstall therefore ends with deleting it (README, Task 7). Probe on 2026-11-18 after `rpm --import`: Fedora 45 (rpm 6.1.0) lists it in `rpmkeys --list` as the full fingerprint in lower case, and `sudo rpmkeys --delete <fingerprint>` removes it. `rpm -e gpg-pubkey-<fingerprint>-<date>` also works but warns "erasing gpg-pubkey packages is deprecated; use rpmkeys --delete". Tumbleweed (rpm 4.20.1) lists it as `<short key id>-<creation date>` (e.g. `e4d2a98f-6afdccd0`); `sudo rpmkeys --delete <short key id>-<creation date>` or `sudo rpm -e gpg-pubkey-<short key id>-<creation date>` removes it, the full fingerprint is not accepted there. dnf5 keeps the keys for `repo_gpgcheck` separately per repository (dnf5.conf(5), below): the container matrix (`docs/distro-check.md`) found its copy in `/var/cache/libdnf5/orbitop-<hash>/pubring/<key id>.pub`, still there after `dnf remove orbitop orbitop-release`, `rpmkeys --delete` and `dnf clean all`, so on Fedora the full uninstall also removes `/var/cache/libdnf5/orbitop-*`. zypper keeps no copy: after `zypper remove`, `rpmkeys --delete` and `zypper refresh`, nothing of the source is left.
  - Version, `%changelog` and build date come only from `packaging/keyring.version`, like `orbitop-apt-source`. `tests/test_packaging_rpm.py` pins its inputs (the spec, both `.repo` files, the committed key, `LICENSE`, the `%changelog`) per version.
  - Reproducible: probe on 2026-11-18 with the throwaway key, built from the same inputs in fresh containers. Fedora 45 (rpm 6.1.0): three builds, all `orbitop-release-2026.11.18-1.noarch.rpm` with sha256 `a268fd38c78d3d71e5c0e514573782b55b9ed1dd98a427962ad5821c52d71a3d`. Tumbleweed (rpm 4.20.1): two builds, both `7d08edf3869a92192fadc5e193955314334550d7784b2a8c50bf1558ca0e286d`. After `type=rpm-md` and `pkg_gpgcheck=1` were added, the two full builds of 2026-11-18 (normal and `--suffix check1`) gave `54e41d2ddb4800f679899255dab873934095b1850cbdc5844cf1887574909e65` both times; the Fedora package stayed `a268fd38…`. The `orbitop` RPMs were byte-identical too. Only the toolchain of the images and their mirrors is not pinned.
- Install probe on 2026-11-18, local files in disposable containers. On Fedora 45, `dnf install ./*.rpm` exits 0 with "skipped OpenPGP checks for 2 packages from repository: @commandline". On Tumbleweed, `zypper install --allow-unsigned-rpm ./*.rpm` exits 0; `python3 >= 3.12` resolves to `python313`. On both, `orbitop --version` works and `rpm -V` is clean. `zypper lr -p` lists `orbitop` with priority 100 next to `repo-oss` with 99. Its GPG column shows `( p)` before the first refresh: in a fresh container every combination of `gpgcheck`, `repo_gpgcheck` and `pkg_gpgcheck`, and `repo-oss` itself, shows `( p)`, and `repo-oss` shows `(r )` once refreshed. The column reports the state, not the file. After `remove`, no path of either package is left, and on openSUSE `/etc/pki/rpm-gpg` is gone too. Signed packages, `repo_gpgcheck` against a served repository and the first key question come with Task 5 and the container matrix.

Arch specifics:

- `packaging/arch/PKGBUILD` with `orbitop.install`, built in `archlinux:latest` by the unprivileged user `builder` (makepkg refuses root), `PACKAGER` the noreply address. `build-inside.sh` puts `pkgver` and `pkgrel` in front of a copy of the `PKGBUILD`. It provides the sources (the archive as `orbitop-<version>.tar`, the binary key `orbitop.gpg`, `orbitop-trusted`) and appends their sums with `makepkg --geninteg`. The `PKGBUILD` does not use `$startdir`, which PKGBUILD(5) calls deprecated.
- `depends=('python>=3.12' python-gobject gtk4 webkitgtk-6.0 glib2 hicolor-icon-theme polkit)`. `glib2` (Gio, GLib) and `hicolor-icon-theme` (the icon) were added because namcap reports them as `E:` "detected and not included" and the Arch package guidelines forbid relying on transitive dependencies (below). `optdepends=('intel-gpu-tools: Intel GPU load of all processes')`. Before `makepkg`, the build installs the `depends` from the repositories as dependencies, so pacman checks every name and namcap sees the packages it analyses.
- `license=('GPL-3.0-or-later' 'OFL-1.1' 'CC0-1.0')`. OFL-1.1 is no common license of Arch; namcap requires its text below `/usr/share/licenses/orbitop/`, so both `OFL-*.txt` are copied there as well.
- Byte code: `python -m compileall` in `package()`, so pacman tracks the caches (Arch Python package guidelines, below). Probe: `python -v` reports `…/__pycache__/sysfs.cpython-314.pyc matches …/sysfs.py`.
- Keyring (pacman-key(8), "Providing a keyring for import"): `/usr/share/pacman/keyrings/orbitop.gpg` (binary) and `orbitop-trusted` with one line `<fingerprint>:3:`. `--populate` locally signs the key, which makes it valid for pacman. The owner trust 3 ("never", in the numbering of `gpg --export-ownertrust`) means the key never helps to validate another key in pacman's keyring. `archlinux-trusted` uses 4 ("marginal"), because three Arch master keys together validate the packager keys; orbitop has no such role. Three checks keep the 3: `tests/test_packaging_arch.py` reads `build-inside.sh` and, where `bwrap` may create a user namespace, the package of a test build of `build-inside.sh` in `bwrap`; the matrix checks the file of the installed package in the step `install` (`docs/distro-check.md`). `orbitop.install` runs `pacman-key --populate orbitop` in `post_install` and `post_upgrade`, like `archlinux-keyring` only when `pacman-key -l` works; otherwise it prints a hint to run `pacman-key --init` and `pacman-key --populate orbitop`.
- Install probe on 2026-11-18 (`pacman -U` of the local file): pacman prints "Locally signing trusted keys in keyring" and "Importing owner trust values", and the key then has validity `f` and owner trust `n` (never). `pacman -Qkk orbitop` reports 0 altered files. After `pacman -R orbitop`, no file of the package is left. The key stays in pacman's keyring; the README explains `pacman-key --delete` (spec 3). The docker image ships pacman's keyring but no local master key. There `pacman-key -l` works, so `--populate` runs and fails with "There is no secret key available to sign with"; pacman prints "command failed to execute correctly", and the installation still succeeds. Without any keyring (`/etc/pacman.d/gnupg` removed), `orbitop.install` prints only its hint. A real Arch system creates the master key during installation; the container matrix (Task 6) has to run `pacman-key --init` first.

## Site

`GNUPGHOME=<dir> ORBITOP_KEY=<fingerprint> bash scripts/build-site.sh --packages DIR --out SITE` turns the output of `build-packages.sh` into the signed tree of the `gh-pages` branch (spec 2). `GNUPGHOME` is a GnuPG directory of its own that holds only the archive key (below). `SITE` must be empty or missing, and each package must be in `DIR` exactly once, as a regular file, so the source holds only the newest version. In-container scripts, the tool image recipe and `index.html` come from `git archive HEAD`, never from local files.

```text
index.html  .nojekyll  orbitop-archive-keyring.asc  orbitop-archive-keyring.pgp
apt/dists/stable/InRelease, Release, Release.gpg, main/binary-all/Packages, Packages.gz,
                 main/binary-all/by-hash/SHA256/<sha256> and by-hash/SHA512/<sha512> (copies of both)
apt/pool/main/o/orbitop/orbitop_<version>-1_all.deb
apt/pool/main/o/orbitop-apt-source/orbitop-apt-source_<keyring.version>_all.deb
rpm/fedora/ and rpm/opensuse/: orbitop-<version>-1.noarch.rpm, orbitop-release-<keyring.version>-1.noarch.rpm,
                               repodata/ (createrepo_c) with repomd.xml, repomd.xml.asc, repomd.xml.key
arch/x86_64/orbitop-<version>-1-any.pkg.tar.zst, orbitop.db, orbitop.files, each with .sig
```

The small source packages are in the source too, so a renewed key arrives with the regular update. The directory names, the suite and the component are constants at the top of `build-site.sh`; `tests/test_site.py` keeps them equal to `orbitop.sources` and the `.repo` files. `index.html` comes from `packaging/site/index.html`: English and German, static, no script, no external loads, one link to the README; the script replaces `<FINGERPRINT>` with the fingerprint of `ORBITOP_KEY` in the grouping of `gpg --fingerprint`.

How it signs:

- Before any container starts: `ORBITOP_KEY` must be the fingerprint of a primary key whose secret key is in `GNUPGHOME`; the gpg-agent of `GNUPGHOME` must list this key in `KEYINFO --list` and no keygrip of another key; it must have its extra socket. The public key is exported from `GNUPGHOME` with `export-minimal` (no certifications by other keys). Every gpg call runs with `--no-options`, so no `comment`, `sig-notation`, `sender` or `armor` from a `gpg.conf` reaches the site. Each container gets only this public key on stdin and compares it byte by byte with the key the packages install (`orbitop-apt-source`, `orbitop-release`, the Arch package). If they differ, the script stops: every client would reject a source signed with another key.
- Only gpg on the host signs, always with `--local-user <fingerprint>!` (exactly the primary key). Before the script ends, `gpgv` checks every signature against a keyring that holds only the exported public key.
- apt: `packaging/site/apt-inside.sh` in `debian:trixie` writes `Packages`, `Packages.gz`, their by-hash copies and `Release` with `apt-ftparchive`: `Origin` and `Label` `orbitop`, `Suite` and `Codename` `stable`, `Components: main`, `Architectures: all` (see "Debian specifics"), `Acquire-By-Hash: yes`, no `Valid-Until` (spec 2). `Packages` and `Release` carry only SHA256 and SHA512: `APT::FTPArchive::MD5` and `APT::FTPArchive::SHA1` are `false` (apt-ftparchive(1)), and `check-apt-index.py` refuses an MD5 or SHA1 field. apt 2.4.15 (Ubuntu 22.04), 2.6.2 (Debian 12), 2.8.4 (Ubuntu 24.04), 3.0.4 (Debian 13) and 3.2.1 (Ubuntu 26.04) accepted such a signed source without a message and installed from it (probe on 2026-11-20). `apt-ftparchive` skips a file that is no package and still exits 0, so the script stops unless `Packages` lists exactly `orbitop` and `orbitop-apt-source`. The container's index is then checked on the host by `packaging/site/check-apt-index.py` (`python3 -I`, from `git archive HEAD`) before anything is signed: the apt tree holds only the two input debs, `Release`, `Packages`, `Packages.gz` and their by-hash copies, each byte-equal to the file it is named after; `Packages.gz` decompresses to `Packages`; each of the two stanzas is the deb's own control file plus its true `Filename`, `Size` and hashes (so no `Depends`, `Conflicts` or version can be forged); `Release` lists exactly `Packages` and `Packages.gz` with their true sizes and hashes and no fields but the ones above and `Date`, in the form `apt-ftparchive` writes it (RFC 2822, `+0000`) and at most 10 minutes ahead of the host clock (an allowance for clock skew; apt itself refuses a `Date` more than `Acquire::Max-FutureTime` ahead, 10 seconds by default, apt.conf(5)). Both files are read like apt reads them, as bytes without newline translation: only an empty line ends a stanza, so a line of blanks (which apt reads as a continuation line), a control character or whitespace other than space and tab is refused. Otherwise the script stops, and the host signs nothing. The host writes `InRelease` (`gpg --clearsign`) and `Release.gpg` (`gpg --armor --detach-sign`).
- RPM: first `docker build` makes a local tool image per family from `packaging/site/rpm-tools.Dockerfile`, `orbitop-site-rpm-fedora:local` from `fedora:latest` and `orbitop-site-rpm-opensuse:local` from `opensuse/tumbleweed`, with that family's `rpmsign`, `createrepo_c` and gpg. The installation runs there, with network and without the socket. `packaging/site/rpm-inside.sh` then runs in these images with `--network none`, so no package is installed, no scriptlet runs and nothing is downloaded while the socket is mounted. `rpmsign --addsign --define "_gpg_name <fingerprint>!"` reaches the host gpg-agent only through its extra socket, bind-mounted with `--mount type=bind` (which fails if the socket is gone) at `/gnupg/S.gpg-agent`. gpg in the container has the public key and `no-autostart`, nothing else. gpg-agent(1) intends this socket for exactly this: signing elsewhere "without exposing the private keys" (below). Without the socket, or if `rpmsign` fails, the script stops; there is no other way, and never a key file in the container. The tool image's own keys leave the rpm database first, so that `rpm -K` accepts the public key alone. An RPM that already verifies with it keeps its bytes and is not signed again: `orbitop-release` of an earlier release, which `release.sh` reuses (Release, step 2). Then `rpm -K` with only the public key must report `digests signatures OK`, and `createrepo_c` writes `repodata/`. The host writes `repomd.xml.asc` (`gpg --armor --detach-sign`) and `repomd.xml.key` (the armored public key). The signed RPMs differ from the unsigned ones in `DIR`, and from build to build, because the signature carries its time.
- Arch: `packaging/site/arch-inside.sh` in `archlinux:latest` with `--network none` runs `repo-add` without a key and turns `orbitop.db` and `orbitop.files` into regular files (Pages serves no symlinks). The host writes a binary `.sig` beside the package and both databases. pacman 7.1 fetches the package's `.sig` from the server; `repo-add` embeds package signatures only with `--include-sigs` (below), which is not needed.

GnuPG directory of its own (spec 4, plan "Schlüssel"):

- Through the extra socket, a process in the container can ask the agent to sign or decrypt with every secret key the agent holds, not only with the archive key, and it can send `GET_PASSPHRASE` to make the agent show a passphrase prompt with a text of its choosing. The agent for a release therefore holds the archive key and nothing else: a `GNUPGHOME` of its own, e.g. `$HOME/.local/share/orbitop-release/gnupg` (mode 0700), which starts its own gpg-agent with its own sockets. `build-site.sh` refuses an agent that lists any other keygrip. A passphrase prompt during a release belongs to the archive key; enter the passphrase only in the prompt that names it, and expect exactly two per run (Release, "The passphrase"). The directory holds no smartcard keys, and no token is plugged in during a release: the agent's scdaemon could reach a token's keys, which `KEYINFO --list` does not show.
- Afterwards: `gpgconf --homedir <dir> --kill all` stops that agent. The tool images stay in the local docker cache; `docker image rm orbitop-site-rpm-fedora:local orbitop-site-rpm-opensuse:local` removes them, the next run builds them again.

Container output: every container runs with `--cap-drop MKNOD --cap-drop SETFCAP` and writes only its part of `SITE` (`/out`); the in-container scripts and the key are read-only or on stdin. After each container, its directory may hold only regular files and directories without setuid or setgid bits, and `getcap -r` must report nothing (it exits 0 even on errors, so any output, an error of `find` or a missing `getcap` stops the script too). Otherwise the script stops before any host tool reads or writes there. A symlink planted there would make `gpg -o` or `cp` write elsewhere on the host, a FIFO would block gpg, a root-owned file with setuid or a capability would hand root's rights to whoever runs it. After the apt and the Arch step, every package there must still have the sha256 it had when it was copied from `--packages`. After the RPM and the Arch step, the directory must hold exactly the files that step writes, or the script stops before it signs anything there (final security audit, F3): in `rpm/<family>/` the two RPMs from `--packages`, `repodata/repomd.xml` and `repodata/<sha256>-primary.xml.zst`, `-filelists.xml.zst` and `-other.xml.zst` (createrepo_c 1.2.6 on Fedora 45 and 1.2.3 on Tumbleweed write `.zst`; `.gz` and `.xz` are accepted too), in `arch/x86_64/` the package, `orbitop.db` and `orbitop.files` (the host adds the `.sig` files afterwards). rpmsign changes the RPMs on purpose, so `packaging/site/rpm-same.py` (`python3 -I`, from `git archive HEAD`) checks on the host that each signed RPM is byte for byte its input from `--packages` from the main header on. It skips the 96-byte lead and the signature header with its padding to 8 bytes: what a client installs, header and payload, is the built package, and only the signature differs. `rpm -K` in the same container checks the signature itself; a bad one would only make clients refuse the package. No package a container replaced or added gets a signature from the host or reaches the site. `--packages DIR` is checked the same way before anything is copied, and every package must be a regular file, not a symlink: `build-packages.sh` wrote it from containers running as root.

Trust boundary: the official base images (`debian`, `fedora`, `opensuse`, `archlinux`) and their mirrors are the trust anchor, for building the packages (`build-packages.sh`) and for indexing them here. The host-side checks protect the host's files (container output, above), refuse foreign or changed content (a package whose sha256 changed, an RPM changed beyond its signature, a file that no step writes, a key other than the one of `ORBITOP_KEY`, a signature over anything but the host's own copy) and verify the apt index. There is deliberately no host-side check of the content of the Arch `orbitop.db` and `orbitop.files` or of the index files in the RPM `repodata/`: the same images build the packages themselves, so a compromised image could put anything into a package anyway. Each build container writes only into a directory of its own (Build), so an image reaches only the packages of its own format. The container that signs the RPMs has no network and installs nothing while the socket is mounted (RPM bullet above, "GnuPG directory of its own").

First trust: the README with the fingerprint, the release files and the site with the key all come from the GitHub account `zappelmann-sketch`. Whoever controls that account controls what a new user checks the key against, so the first trust in the key rests on the account alone; the fingerprint in the README is no check independent of it. Every update after the first installation is checked with the key the system already has.

Who verifies what:

- apt checks `InRelease` against `/etc/apt/keyrings/orbitop-archive-keyring.pgp` (`Signed-By`), and each package by its hash in the signed `Packages`.
- dnf checks `repomd.xml.asc` (`repo_gpgcheck=1`) and the signature in each package (`gpgcheck=1`) with the key named in `gpgkey=`.
- zypper checks `repomd.xml.asc` and, with `pkg_gpgcheck=1`, each package (per zypper(8); that zypper refuses a package with a bad signature was not probed).
- pacman checks `orbitop.db.sig` (`DatabaseRequired`) and the package's `.sig` (`Required`) with the key that `pacman-key` trusts.

Only apt binds the key to this source (`Signed-By`). The rpm database and pacman's keyring are global: once the key is in them (`rpm --import`, the import by dnf or zypper on the first use, `pacman-key --lsign-key` or `--populate orbitop`), rpm, dnf, zypper and pacman accept it for the packages and indexes of every repository on that machine, not only of this one. Whoever has the secret key could sign packages for another repository there. Both READMEs say so next to the key import and point to the full uninstall, which removes the key again.

Freshness and caching (accepted risks, spec 2 and 10):

- No format carries an expiry the clients check: `Release` has no `Valid-Until` (spec 2), and neither `repomd.xml` nor the pacman database has a freshness field. Whoever controls the delivery can serve an older, validly signed state until the key expires ("freeze"), and clients do not notice.
- Fedora: dnf5 uses `skip_if_unavailable=True` by default (Fedora 45, dnf5 5.4.6: `/usr/share/dnf5/libdnf.conf.d/20-fedora-defaults.conf`, `dnf5 --dump-main-config` shows `skip_if_unavailable = 1`; Fedora's own `fedora.repo` sets `False`), and `orbitop-fedora.repo` keeps the default: an outage of GitHub Pages must not stop the system update. A `repomd.xml` with an invalid signature is therefore skipped with the message "repomd.xml GPG signature verification error: Bad PGP signature", and `dnf` still exits 0: a bad signature, too, looks like a silent freeze. dnf never installs from it.
- GitHub Pages caches each file for itself, about 10 minutes. Right after a release a client may get a new `InRelease` with an old `Packages`; `Acquire-By-Hash` lets apt fetch the index by its hash, so it never mixes the two. `repomd.xml` with `repomd.xml.asc`, and `orbitop.db` or `orbitop.files` with their `.sig`, can briefly mismatch: the client then reports a bad signature and retries on the next refresh. The data files of `repodata/` carry their hash in the name. The final check of plan 2026-11-18 (Task 10) looks at the published state after the cache time.

Probe on 2026-11-18 after the security audit, with a fresh throwaway key (Ed25519, no passphrase) in a `GNUPGHOME` of its own whose `gpg.conf` held `comment`, `sig-notation` and `armor`; the packages from `build-packages.sh` (all four formats build with `--cap-drop MKNOD`), the site served read-only via `file://` in disposable containers:

## Key

The archive key (spec 4): an Ed25519 primary key that signs directly, without a subkey, user ID `orbitop archive signing key` without a mail address, valid for 3 years, protected by a passphrase. It lives in a GnuPG directory of its own with its own gpg-agent (Site, "GnuPG directory of its own"), on the maintainer's machine and nowhere else: never in the repository, an image, a container or at GitHub. The maintainer made it once like this (plan 2026-11-18, Task 9); `$HOME/.local/share/orbitop-release/gnupg` stands for that directory:

```sh
export GNUPGHOME="$HOME/.local/share/orbitop-release/gnupg"
mkdir -p -m 700 "$GNUPGHOME"
echo disable-scdaemon > "$GNUPGHOME/gpg-agent.conf"
gpg --quick-gen-key "orbitop archive signing key" ed25519 sign 3y
gpg --list-secret-keys --with-colons | awk -F: '$1 == "fpr" { print $10; exit }'
```

- `disable-scdaemon`: this agent never starts scdaemon, so no key on a smartcard or token is reachable through its extra socket while `rpmsign` uses it.
- `--quick-gen-key` with `sign` makes one primary key that signs and certifies and no subkey; pinentry asks for the passphrase. gpg also writes a revocation certificate, `$GNUPGHOME/openpgp-revocs.d/<fingerprint>.rev` (gpg(1), Sources).
- The last line prints the fingerprint, the `ORBITOP_KEY` of every release. It goes into both READMEs in place of `<FINGERPRINT>`, the public key goes to `packaging/keys/orbitop-archive-keyring.asc` (`gpg --armor --export --export-options export-minimal "$ORBITOP_KEY"`), and the date of the key to `packaging/keyring.version` (plan 2026-11-18, Task 9). `release.sh` refuses a key that differs from that file or from the README.

## Backup to KeePassXC

Three exports to `$XDG_RUNTIME_DIR`, which is in memory and readable only by the user: the secret key (armored, still protected by the passphrase), the public key and the revocation certificate.

```sh
export ORBITOP_KEY=<fingerprint>
out="$XDG_RUNTIME_DIR/orbitop-key"
mkdir -m 700 "$out"
gpg --armor --export-secret-keys "$ORBITOP_KEY" > "$out/orbitop-archive-key.secret.asc"
gpg --armor --export --export-options export-minimal "$ORBITOP_KEY" > "$out/orbitop-archive-keyring.asc"
cp "$GNUPGHOME/openpgp-revocs.d/$ORBITOP_KEY.rev" "$out/"
```

Before the exports go, a restore test in a temporary directory, also in memory: the import and the signature each ask for the passphrase.

```sh
check=$(mktemp -d -p "$XDG_RUNTIME_DIR")
gpg --homedir "$check" --import "$out/orbitop-archive-key.secret.asc"
echo test | gpg --homedir "$check" --local-user "$ORBITOP_KEY!" --clearsign > /dev/null && echo "restore works"
gpgconf --homedir "$check" --kill all
rm -rf "$check"
```

Then the three files become attachments of one KeePassXC entry. Create the entry first, in the window: title `orbitop archive signing key`, password the passphrase. Attach the files there (entry, Advanced, Attachments, Add) or with `keepassxc-cli` (2.7.10: `attachment-import [options] database entry attachment-name import-file`). Only the maintainer opens the database; `keepassxc-cli` asks for its password.

```sh
db=<database>.kdbx
entry="orbitop archive signing key"
for file in orbitop-archive-key.secret.asc orbitop-archive-keyring.asc "$ORBITOP_KEY.rev"; do
    keepassxc-cli attachment-import "$db" "$entry" "$file" "$out/$file"
done
rm -r "$out"
```

## Restore

A new GnuPG directory of its own, as in "Key", then the secret key from the KeePassXC entry (the import asks for the passphrase); the export is deleted right after.

```sh
export ORBITOP_KEY=<fingerprint>
db=<database>.kdbx
entry="orbitop archive signing key"
export GNUPGHOME="$HOME/.local/share/orbitop-release/gnupg"
mkdir -p -m 700 "$GNUPGHOME"
echo disable-scdaemon > "$GNUPGHOME/gpg-agent.conf"
out="$XDG_RUNTIME_DIR/orbitop-key"
mkdir -m 700 "$out"
keepassxc-cli attachment-export "$db" "$entry" orbitop-archive-key.secret.asc "$out/orbitop-archive-key.secret.asc"
gpg --import "$out/orbitop-archive-key.secret.asc"
rm -r "$out"
gpg --list-secret-keys "$ORBITOP_KEY"
```

`bash scripts/release.sh <version> --dry-run` then shows whether the key is complete: it refuses a `GNUPGHOME` without the secret key of `ORBITOP_KEY`, and `build-site.sh` signs and verifies every index with it.

## Renewal

`release.sh` warns when the key has less than 180 days left and refuses an expired key. Extend it in time, while it is still valid, so that every system gets the extension with a regular update:

1. `gpg --quick-set-expire "$ORBITOP_KEY" 3y` (pinentry): the same key with the same fingerprint and a new self-signature, valid for 3 years from that day. The README's fingerprint stays.
2. Export the public key again to `packaging/keys/orbitop-archive-keyring.asc` and set `packaging/keyring.version` to that day. `tests/test_packaging_debian.py` and `tests/test_packaging_rpm.py` pin the inputs of `orbitop-apt-source` and `orbitop-release` per version, so their pinned hashes change with it. A new `keyring.version` is a new version of both small packages; without it the source would offer the old version with a new key.
3. Back up again ("Backup to KeePassXC"): the secret export carries the new self-signature.
4. A release delivers it: `orbitop-apt-source` replaces `/etc/apt/keyrings/orbitop-archive-keyring.pgp` (a conffile only the package changes, so dpkg replaces it without asking), `orbitop-release` replaces `RPM-GPG-KEY-orbitop` (not `%config`), and `orbitop.install` runs `pacman-key --populate orbitop`. Before that release, check in containers that dnf and zypper still accept the source after the old expiry date: the rpm database keeps the key as it was first imported, and the matrix does not cover this, because it installs fresh.
5. The full uninstall of the README selects keys by user ID, not by fingerprint, so it removes every key with the user ID `orbitop archive signing key`, also one that an update brought. A key with another user ID would stay behind on users' systems.

## Revocation

When someone else may have the secret key with its passphrase, or both are lost.

No client downloads a key file again after the installation: apt reads only `/etc/apt/keyrings/orbitop-archive-keyring.pgp`, a conffile of `orbitop-apt-source` (`Signed-By`); dnf and zypper keep the key they imported first in the rpm database; pacman trusts what `pacman-key --populate orbitop` took from the orbitop package. A revoked key on `gh-pages` reaches only new users. The way to installed systems is an update signed with a key they still trust:

1. Make a new key ("Key"), with a new fingerprint in both READMEs and a new `packaging/keyring.version`.
2. While the old key is still valid and at hand, one last release signed with it. Its `orbitop-apt-source` carries the new key next to the old one in `orbitop-archive-keyring.pgp`. Its Arch package carries the new key in `orbitop.gpg` and `orbitop-trusted` and a file `orbitop-revoked` with the old fingerprint: `pacman-key --populate orbitop` in `post_upgrade` disables the keys listed there (pacman-key(8), "Providing a keyring for import"). Its `orbitop-release` carries the new key in `RPM-GPG-KEY-orbitop`. Today `build-site.sh` and `release.sh` require that every package carries exactly the key of `ORBITOP_KEY`, so this release needs that changed first.
3. From the next release on, the source is signed with the new key, and `orbitop-apt-source` carries only the new key. Systems that did not update in between fail `apt update` and need the source set up anew (README, full uninstall, then the installation).
4. RPM: dnf and zypper keep the old key in the rpm database, where it stays trusted for every repository ("Who verifies what"); no package can remove it. Users delete it by hand: `sudo rpmkeys --delete <old fingerprint in lower case>` on Fedora, `sudo rpmkeys --delete <short key id>-<creation date>` on openSUSE (`rpmkeys --list`, "RPM specifics"). The uninstall line of the README selects by user ID and would delete the new key as well, which has the same one. Whether dnf and zypper take the new key from the updated `RPM-GPG-KEY-orbitop` without asking is the open question of "Renewal", step 4; probe it in containers before that release.
5. The revocation certificate: take `<fingerprint>.rev` from the KeePassXC entry, remove the colon gpg put before `-----BEGIN PGP PUBLIC KEY BLOCK-----` against accidental use, and `gpg --import` it into a GnuPG directory with the public key. The release notes and a GitHub issue carry the revoked key (`gpg --armor --export`) and the steps above, so that users can check it and act.

If the old key is lost or misused before step 2, no update reaches the systems. The release notes and a GitHub issue then tell users to remove the source (README, full uninstall; on Fedora and openSUSE the old key by its fingerprint as in step 4) and to install it anew after comparing the new fingerprint.

## Lint notes

Lintian (Debian trixie) runs with `--display-info --show-overrides` on both `.deb` files in every build. There is no `E:` tag. One tag is overridden, and each remaining `W:` and `I:` tag of `orbitop` is accepted for the reason below.

- `O: orbitop-apt-source: package-installs-apt-preferences [etc/apt/preferences.d/orbitop.pref]`, an error tag overridden in `packaging/apt-source/debian/orbitop-apt-source.lintian-overrides`. This is the only override (test).
  - Lintian flags every file under `etc/apt/preferences.d/`. Its check exempts only the source package `apt`, unlike `package-installs-apt-sources` (`*-apt-source`) and `package-installs-apt-keyring` (`*-apt-source`, `*-archive-keyring`). No package name avoids the tag.
  - DebianRepository/UseThirdParty (above) lets the keyring package "also include […] the /etc/apt/preferences.d/deriv.pref file" and requires that "the preferences file MUST allow automatic upgrades (Pin-Priority: 100)".
  - Without the file, the repository could replace packages of the distribution; the same page says that without it "the user MUST be warned of the security consequences".

- `W: orbitop: no-manual-page [usr/bin/orbitop]`: Debian Policy 12.1 says a program "should" have a manual page. orbitop is a graphical program with two options (`--version`, `--hidden`), described in the README. A manual page is a possible later addition.
- `I: orbitop: font-in-non-font-package` and `I: orbitop: font-outside-font-dir` for `Orbitron.ttf` and `Oxanium.ttf`: the fonts belong to the page in the WebView, which loads them as `orbitop://ui/fonts/…`. The scheme handler serves only `orbitop/ui/`, and system-wide fonts would appear in every font menu.
- `I: orbitop: package-contains-documentation-outside-usr-share-doc` for `ui/index.html`, `ui/fonts/OFL-Orbitron.txt` and `ui/fonts/OFL-Oxanium.txt`: `index.html` is the user interface, not documentation. The OFL texts travel next to their fonts, as the OFL requires, and the app serves them from there; `debian/copyright` carries the license as well.

rpmlint runs once per family over both RPMs: rpmlint 2.9.0 with Fedora's configuration and rpmlint 2.10.0 with openSUSE's. There is no rpmlintrc. The "filtered" counts in the reports come from the distributions' own configurations. The build fails on every `E:` line except the one below, because openSUSE's rpmlint exits 0 below its badness threshold even when it reports an error.

- `E: orbitop: polkit-untracked-privilege (Badness: 10) io.github.zappelmann-sketch.orbitop.terminate (auth_admin:auth_admin:auth_admin)`, openSUSE only. It is the only accepted error, matched as this exact line in `packaging/rpm/lint-gate.sh`. The gate reads the report with one `awk`, without a pipe that could end early (an earlier `grep | grep -q` let a long report pass), and fails if the summary line of rpmlint is missing (`tests/test_packaging_rpm.py`).
  - openSUSE's rpmlint reports every polkit action that the SUSE security team has not reviewed and listed in `polkit-default-privs`. It asks for that review "if the package is intended for inclusion in any SUSE product"; orbitop is not, it comes from its own package source.
  - `opensuse.toml` puts the tag under `BlockedFilters`, so no rpmlintrc can filter it. That is why the build script accepts the line instead.
  - The line names the action and its defaults: if an action weaker than `auth_admin` appears, the line differs and the build fails.
  - For actions outside its profiles, `polkit-default-privs` adds no rule, so polkit applies the `.policy` defaults `auth_admin` (Sources, above).
- `W: orbitop: only-non-binary-in-usr-lib` (Fedora): `/usr/lib/orbitop/` holds only the helper, a Python script that pkexec starts directly (K1). It is an internal program, not data for `/usr/share`. Fedora's Libexecdir section accepts `%{_libdir}/%{name}`, and `/usr/libexec` is no option for Arch (Sources, above).
- `W: orbitop: no-manual-page-for-binary orbitop` (Fedora): as `no-manual-page` above.
- `W: orbitop: no-documentation` and `W: orbitop-release: no-documentation` (Fedora): both packages carry only their license (`%license`); the README lives in the repository. The Fedora guidelines require no `%doc`.
- `W: orbitop-release: non-conffile-in-etc /etc/pki/rpm-gpg/RPM-GPG-KEY-orbitop` (Fedora and openSUSE): the key is deliberately no `%config`, like `/etc/pki/rpm-gpg/RPM-GPG-KEY-openSUSE` of `rpm-repo-keys-openSUSE`. With `%config(noreplace)`, rpm would keep a changed or old key and save a renewed one only as `.rpmnew`; without it, every update installs the current key.

namcap runs on the `PKGBUILD` and on the package, after the runtime dependencies are installed. There is no `E:` tag (the two missing dependencies and the missing OFL license text were fixed, see "Arch specifics"), the `PKGBUILD` gets no tag, and no tag is filtered. The remaining warnings of the package:

- `W: Referenced python module 'orbitop.…' is an uninstalled dependency` (48 lines, one per imported name such as `orbitop.gpu.GpuReader`): namcap looks for orbitop's own modules in the Python path of the system. They live in the private directory `/usr/share/orbitop/orbitop/` (K2) and are part of this package.
- `W: Referenced library 'python3' is an uninstalled dependency` for `usr/lib/orbitop/killhelper`, `usr/share/orbitop/bin/orbitop` and `usr/share/orbitop/orbitop/killhelper.py`: namcap takes the name `python3` from the shebang `#!/usr/bin/python3` and finds no package of that name. `/usr/bin/python3` belongs to the package `python`, which is in `depends` as `python>=3.12`. The helper's shebang `#!/usr/bin/python3 -I` must stay (K1).
- `W: Dependency included, but may not be needed ('polkit')`: orbitop starts `pkexec` from `polkit` at run time to end foreign processes (`orbitop/actions.py`); namcap cannot see a program that is started by path.
