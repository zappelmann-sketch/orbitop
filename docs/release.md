# Release and packaging

How the orbitop packages are built, which rules they follow, and why the remaining lint tags are accepted.

## Build

`bash scripts/build-packages.sh --out DIR --pubkey FILE [--suffix SUFFIX]` builds from `git archive HEAD` in a disposable `debian:trixie` container (`docker run --rm`, the archive read-only, only `DIR` writable):

- `DIR/deb/orbitop_<version>-1_all.deb` and `DIR/deb/orbitop-archive-keyring_<packaging/keyring.version>_all.deb`
- `DIR/lint/<package>.txt`: the lintian report of each package; the script exits non-zero on an `E:` tag
- `FILE` is the armored public key of the package source. The script refuses anything else, so a secret key never reaches the container.
- `--suffix check1` builds `<version>-1+check1`, a check build that is never published (update test in the container matrix).

`packaging/install-tree.sh DESTDIR` lays out the file tree of the main package; every package format uses it. `packaging/changelog.py` writes the Debian changelog (and the RPM `%changelog`) from the `<release>` entries of the metainfo, the only source; the repository holds no `debian/changelog`.

Debian specifics:

- `dh_python3` byte-compiles `/usr/share/orbitop` in `postinst` and removes the byte code in `prerm` (Python Policy 5.3, below). It runs with `--no-shebang-rewrite`: otherwise it turns the helper's `#!/usr/bin/python3 -I` into `#! /usr/bin/python3` and drops `-I`. The build script fails if the packaged helper differs from `orbitop/killhelper.py`.
- `orbitop.sources` has no `Architectures` field. Probe on 2026-11-18 with a signed `file://` copy of the source (`Release` with `Architectures: all`, only `main/binary-all`): Debian 13 (apt 3.0.4), Ubuntu 24.04 (apt 2.8.4) and Ubuntu 26.04 (apt 3.2.1) print the same lines with and without `Architectures: all`, no `W:`, `E:` or `N:`, exit 0, candidate found. The `Release` file of the source must therefore keep `Architectures: all`.
- The keyring package takes its version from `packaging/keyring.version` (`dh_gencontrol -v`), not from orbitop; the main package does not depend on it (K3).

## Sources

Read on 2026-11-18 before building. Quotes are verbatim.

- **Debian Policy 4.7.4.1, 9.1.1 "File System Structure"**, <https://www.debian.org/doc/debian-policy/ch-opersys.html#file-system-structure>:
  "The location of all files and directories must comply with the Filesystem Hierarchy Standard (FHS), version 3.0, with the exceptions noted below". Exception 1: "a subdirectory of /usr/lib may be used by a package (or a collection of packages) to hold a mixture of architecture-independent and architecture-dependent files. However, when a directory is entirely composed of architecture-independent files, it should be located in /usr/share." The policy does not mention `/usr/libexec` itself.
- **FHS 3.0, 4.6 "/usr/lib"**, <https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04s06.html>: "On some systems, it may also include internal binaries that are not intended to be executed directly by users or shell scripts. Applications may use a single subdirectory under /usr/lib." 4.7 "/usr/libexec", <https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04s07.html>: "Applications which use /usr/libexec in this way must not also use /usr/lib to store internal binaries […] Either practice is now acceptable, but each application must choose one way or the other".
  Result for the root helper (K1): `/usr/lib/orbitop/killhelper`. It is an internal program, not a static data file, so the "should be located in /usr/share" sentence above does not apply; orbitop keeps all internal programs in `/usr/lib/orbitop`.
- **Debian Policy 4.7.4.1, 9.1.2 "Site-specific programs"**, same page: "As mandated by the FHS, packages must not place any files in /usr/local, either by putting them in the file system archive to be unpacked by dpkg or by manipulating them in their maintainer scripts." This is why the helper moved away from `/usr/local/libexec/orbitop/`.
- **Debian Policy 4.7.4.1, 10.7.3 "Behavior"**, <https://www.debian.org/doc/debian-policy/ch-files.html#behavior>: "configuration files must be preserved when the package is removed, and only deleted when the package is purged." A conffile's default version "must not be modified by the maintainer scripts during installation (or at any other time)." **10.7.4 "Sharing configuration files"**: "The maintainer scripts must not alter a conffile of any package, including the one the scripts belong to."
  Result (K3): the apt source is a conffile of its own package `orbitop-archive-keyring`, together with the key it names. Removing `orbitop` leaves both in place, so `apt update` keeps working; purging the keyring package removes both.
- **Debian Python Policy, 5.3 "Programs Shipping Private Modules"**, <https://www.debian.org/doc/packaging-manuals/python-policy/#programs-shipping-private-modules>: "These modules should be installed in /usr/share/module, or /usr/lib/module if the modules are architecture-dependent (e.g. extensions). […] the byte-compiled modules must not be shipped with the binary package, they should be generated in the package's post-install script using the current default Python version, and removed in the pre-remove script."
  Result (K2): the program lives in `/usr/share/orbitop/`; `dh_python3` adds the `py3compile`/`py3clean` calls to `postinst`/`prerm`.
- **Debian Wiki, DebianRepository/UseThirdParty**, <https://wiki.debian.org/DebianRepository/UseThirdParty>: "Certificate updates SHOULD be distributed by a Debian package called deriv-archive-keyring." "This package MUST distribute the certificate in binary form as /usr/share/keyrings/deriv-archive-keyring.pgp" and "MAY also include the /etc/apt/sources.list.d/deriv.sources or /etc/apt/sources.list.d/deriv.list files." "The signed-by entry MUST point to a file, and not a fingerprint." "The certificate MUST NOT be placed in /etc/apt/trusted.gpg.d or loaded by apt-key add."
  Result (K3): `orbitop-archive-keyring` with `/usr/share/keyrings/orbitop-archive-keyring.pgp` and `/etc/apt/sources.list.d/orbitop.sources` (deb822).
- **ArchWiki, Arch package guidelines, "Directories"** (page last edited 2 May 2026; wiki.archlinux.org refused the automated request, so read from package `arch-wiki-docs` 20261101-1 in a disposable `archlinux:latest` container): table rows "/usr/lib/pkg — Modules, plugins, etc." and "/usr/share/pkg — Application data"; "Packages should never be installed to /usr/local/."; "Avoid using /usr/libexec/ for anything. Use /usr/lib/$pkgname/ instead."
  Result: `/usr/lib/orbitop/` for the helper is the one location every format accepts (K1); `/usr/libexec` would not be.
- **polkit(8)**, <https://polkit.pages.freedesktop.org/polkit/polkit.8.html> (also the local man page of polkit 127): "polkit actions are namespaced and can only contain the characters "[A-Z][a-z][0-9].-", e.g. ASCII, digits, period and hyphen. Each XML file can contain more than one action but all actions need to be in the same namespace and the file needs to be named after the namespace and have the extension .policy." "The org.freedesktop.policykit.exec.path annotation is used by the pkexec program shipped with polkit - see the pkexec(1) man page for details."
  Result (K8): action `io.github.zappelmann-sketch.orbitop.terminate` in `/usr/share/polkit-1/actions/io.github.zappelmann-sketch.orbitop.policy`.
- **pkexec(1)**, <https://polkit.pages.freedesktop.org/polkit/pkexec.1.html>: "To use another action, use the org.freedesktop.policykit.exec.path annotation on an action with the value set to the full path of the program." VARIABLES: "The following variables are set by pkexec. They can be used in authorization rules and messages shown in authentication dialogs: […] command_line — The requested command-line (do not use this for any security checks, it is not secure)."
  Result: pkexec starts `/usr/lib/orbitop/killhelper` directly (its shebang `#!/usr/bin/python3 -I`), so the annotation matches only the helper; the dialog message ends in `$(command_line)`.
- **freedesktop.org, Desktop Application Autostart Specification 0.51**, <https://specifications.freedesktop.org/autostart/latest/>: 2.1 "If the same filename is located under multiple Autostart Directories only the file under the most important directory should be used." Its example: "only the file ~/.config/autostart/foo.desktop will be used because ~/.config/autostart/ is more important than /etc/xdg/autostart/". 2.2.1 "When the .desktop file has the Hidden key set to true, the .desktop file MUST be ignored." 2.2.3 "A .desktop file with a non-empty TryExec field MUST NOT be autostarted if the value of the TryExec key does NOT match with an installed executable program." 2.3 "an individual user can disable the automatic start of this application by placing a .desktop file of the same name in their personal autostart directory which contains the key Hidden=true."
  Result (K5): the package ships only the inactive template `/usr/share/orbitop/autostart.desktop` (`TryExec=orbitop`) and never an entry in `/etc/xdg/autostart`.

## Lint notes

Lintian (Debian trixie) runs with `--display-info --show-overrides` on both `.deb` files in every build. There is no `E:` tag. The one overridden tag and each remaining `W:` and `I:` tag is accepted for the reason below.

- `O: orbitop-archive-keyring: package-installs-apt-sources [etc/apt/sources.list.d/orbitop.sources]`, an error tag overridden in `packaging/debian/orbitop-archive-keyring.lintian-overrides`. Lintian allows a file in `sources.list.d` only in packages named `*-apt-source`; the tag guards packages of the Debian archive. For a third-party source, DebianRepository/UseThirdParty (above) lets the keyring package ship the `.sources` file. Source and key stay in one package, so removing `orbitop` never leaves a source without its key, and the first installation is a single file (K3).
- `W: orbitop: initial-upload-closes-no-bugs` and the same for `orbitop-archive-keyring`: the changelog has one entry with revision 1 and closes no ITP bug. orbitop is not uploaded to Debian (spec, non-goals), so there is no ITP. The tag disappears once the metainfo lists a second release.
- `W: orbitop: no-manual-page [usr/bin/orbitop]`: Debian Policy 12.1 says a program "should" have a manual page. orbitop is a graphical program with two options (`--version`, `--hidden`), described in the README. A manual page is a possible later addition.
- `I: orbitop: font-in-non-font-package` and `I: orbitop: font-outside-font-dir` for `Orbitron.ttf` and `Oxanium.ttf`: the fonts belong to the page in the WebView, which loads them as `orbitop://ui/fonts/…`. The scheme handler serves only `orbitop/ui/`, and system-wide fonts would appear in every font menu.
- `I: orbitop: package-contains-documentation-outside-usr-share-doc` for `ui/index.html`, `ui/fonts/OFL-Orbitron.txt` and `ui/fonts/OFL-Oxanium.txt`: `index.html` is the user interface, not documentation. The OFL texts travel next to their fonts, as the OFL requires, and the app serves them from there; `debian/copyright` carries the license as well.
