## 1. Kurzfassung

1. **Helfer:** `/usr/lib/orbitop/counterhelper` (`#!/usr/bin/python3 -IS`, nur Standardbibliothek). `on` und `off` laufen über pkexec mit je eigener polkit-Action (`exec.argv1`, `auth_admin`, nur lokale aktive Sitzungen, E2); `sync` rufen nur die Paket-Skripte. Er nimmt keine Pfade und keine Umgebung, startet kein fremdes Programm (`fsetxattr`, `fchmod`, `dir_fd`), arbeitet unter `flock` mit begrenzter Wartezeit, und `on`/`sync` wirken nur im Init-User-Namespace.
2. **Merkdatei** (E1 = A): `/etc/orbitop/counters-released` (root, 0644) im paketeigenen `/etc/orbitop` (0711, siehe B2.2), gelöscht schon bei „remove“; das ist eine dokumentierte Abweichung von Debian Policy 10.7.3. `/etc`, weil udev beim Start nicht auf `/var` wartet.
3. **RAPL:** Regel `/usr/lib/udev/rules.d/70-orbitop-counters.rules` (`TEST` auf die Merkdatei, `chmod go+r`), anders benannt als die Handregel, die sie sonst verdecken würde. Im Betrieb setzt der Helfer die Rechte selbst, ohne `udevadm trigger`; „aus“ heißt `S_IMODE & 0o600`, also 0400.
4. **perfmon:** `cap_perfmon=ep` nur auf `/usr/bin/intel_gpu_top`, fd-basiert nach der Kettenprüfung. Auslöser rufen `sync`: dpkg `interest-noawait` mit `postinst configure|triggered`, RPM `%filetriggerin` und `%posttrans`, pacman-Hook; `%transfiletriggerin` mit Dateipfad feuert nie. In allen Formaten belegt: Ohne Merkdatei setzt nichts die Fähigkeit.
5. **Zustand ohne root:** `lstat` für die Merkdatei, ein Parser für `security.capability`, der Modus von `energy_uj`; „von Hand“ heißt Wirkung ohne Merkdatei. Das heutige `_has_capability` ist zu grob.
6. **PackageKit:** nur bei `VersionMajor == 1`; `Resolve`, dann `SIMULATE|ONLY_TRUSTED` mit Positivliste, dann `ONLY_TRUSTED`. Namen: apt erst `igt-gpu-tools`, dann `intel-gpu-tools`; zypper und pacman `intel-gpu-tools`; dnf `igt-gpu-tools`. **Fedora installiert für aktive lokale wheel/sudo-Benutzer ohne Passwort** (eigene Regel der Distribution), sonst gilt `auth_admin_keep`; auf Fedora begrenzt nur die harte Vorbedingung: einmal je Sitzung, nur solange `hint.igt_missing` aktiv ist (E3).
7. **Seite:** Nachrichten ohne Textfelder, Zusatzfelder fallen weg; ein Tor für alle Passwortaufträge; die Sperre wächst (10 s, 60 s, nach drei Ablehnungen bis zum Neustart). Die Erklärung in der Seite bleibt als Bedienhilfe, nicht als Schutz (E6).
8. **pkexec-Prüfung** (E5, schon in Plan 1): Vor jedem pkexec-Aufruf muss `/usr/bin/pkexec` eine root-eigene setuid-ELF-Datei sein, sonst `nohelper`. Das wehrt `run0-wrappers` auf openSUSE ab.
9. **Pakete:** Entfernen ruft `off` und danach eine Sicherung; Install und Upgrade rufen `sync`, das ohne Merkdatei nichts tut (E4); kein Skript ruft je `on`.
10. **Zusatzbefunde:** openSUSE braucht `Requires: /usr/bin/pkexec` (betrifft 0.2.0). Auf Ubuntu 26.04 gehört `intel_gpu_top` zu `igt-gpu-tools`, Teil D0 muss dieses Paket entfernen. Die Testversion wird nur als `.deb` gebaut (E7).
11. **Entscheidungen:** E1 bis E7, entschieden vom Controller im Auftrag des Users, 2026-11-19 (Abschnitt 4).

## 2. Bedrohungsmodell

### 2.1 Schutzgüter

| Nr. | Schutzgut | Warum |
|---|---|---|
| A1 | Unversehrtheit von root | Helfer, Paket-Skripte, Auslöser und die udev-Regel laufen als root. |
| A2 | Vertraulichkeit gegenüber Seitenkanälen | Die RAPL- und perf-Zähler erlauben Angriffe auf Kernel-, Enklaven- und fremde Daten (Platypus, 2.4). |
| A3 | Einwilligung des Admins | Anti-Ziel: keine Freigabe ohne ausdrückliches Einschalten, auch nicht nach Update, Neuinstallation oder Umstieg. |
| A4 | Admin-Passwort und Aufmerksamkeit | Schleifen von Passwortdialogen und Phishing über die Seite. |
| A5 | Unversehrtheit der Dateien anderer Pakete | Die Fähigkeit liegt auf einer Datei von `intel-gpu-tools` bzw. `igt-gpu-tools`. |

### 2.2 Angreifer

| Nr. | Angreifer | Kann | Will |
|---|---|---|---|
| T1 | anderes lokales Konto (ohne Admin-Rechte) | `pkexec` mit beliebigen Argumenten aufrufen; PackageKit ansprechen; freigegebene Zähler lesen; `intel_gpu_top` ausführen | root; fremde Daten über Seitenkanäle; eine Freigabe ohne Admin |
| T2 | Prozess des Desktop-Benutzers (gleiche UID wie orbitop) | alles, was orbitop als Benutzer kann, also auch pkexec und PackageKit aufrufen; ptrace nur nach der Yama-Regel; auf Fedora als wheel-Benutzer: über PackageKit **ohne Passwort** installieren (I-2, unabhängig von orbitop) | root oder eine stille Freigabe; Passwort abgreifen |
| T3 | kompromittierte Seite in der WebView | beliebige erlaubte Nachrichten an `parse_message` senden, beliebig oft; eigenen Text zeigen; auf Fedora: eine Installation des festen Pakets **ohne Dialog** auslösen, einmal je Sitzung (B2.6) | Passwortdialog-Schleifen; Phishing; Freigabe oder Installation ohne Wissen des Benutzers |
| T4 | manipuliertes Paket von einem Spiegel | Pakete mit falscher Signatur ausliefern; alte Stände ausliefern | eigenen Code als root oder mit `cap_perfmon` ausführen |
| T5 | Bedienfehler oder Systemkonfiguration des Admins (kein Angreifer, aber Ursache) | Regel von Hand; falsche Rechte; Downgrade; ein pkexec-Ersatz wie `run0-wrappers` (I-3); `fs.protected_hardlinks=0` | – |

T4 mit gültiger Signatur der Distribution oder von orbitop ist gleichbedeutend mit root und liegt außerhalb dieses Modells. Den Schlüssel von orbitop sichert die Stufe-2-Spec.

### 2.3 Vertrauensgrenzen

| Nr. | Grenze | Kontrolle |
|---|---|---|
| V1 | Seite (JS) → Python | `parse_message` (feste Formen) und Vorbedingungen in Python (B2.7) |
| V2 | Benutzer → root über pkexec | Prüfung, dass `/usr/bin/pkexec` das setuid-ELF von polkit ist; polkit `auth_admin` je Aufruf; `exec.path` und `exec.argv1`; feste Wörter; `_trusted` vor dem Aufruf (B2.1) |
| V3 | Benutzer → PackageKit (System-D-Bus) | polkit von PackageKit (auf Fedora für wheel/sudo: `yes`); `ONLY_TRUSTED`; fester Name; Simulation; harte Vorbedingung (B2.6) |
| V4 | Paketverwaltung (root) → Auslöser von orbitop → fremde Datei | Merkdatei als einziger Schalter; `sync` im Lock; Kettenprüfung (B2.4) |
| V5 | Kernel-Zähler → alle Konten | nur nach ausdrücklichem „an“; „aus“ stellt den Kernel-Standard her (B2.3, B2.4) |
| V6 | Systemstart: udev (root) liest die Merkdatei | Merkdatei auf dem root-Dateisystem; root-eigenes Verzeichnis (B2.2) |

### 2.4 Hintergrund: CVE-2020-8694 (Platypus) und was die Freigabe öffnet

- **CVE-2020-8694** (Intel): „Insufficient access control in the Linux kernel driver for some Intel(R) Processors may allow an authenticated user to potentially enable information disclosure via local access.“
  - Die Gegenmaßnahme im Kernel ist Commit 949dd0104c49 „powercap: restrict energy meter to root access“ (November 2020, auch in die stabilen Zweige zurückportiert).
  - Seither hat `energy_uj` den Modus 0400, bei Zonen mit `reset_energy_uj` den Modus 0600.
- **CVE-2020-12912** (AMD) betrifft die RAPL-Schnittstelle der AMD-Erweiterung von hwmon. AMD hat sie daraufhin auf privilegierten Zugriff umgestellt. Der Treiber `amd_energy` wurde erst eingeschränkt und später entfernt. orbitop liest ihn nicht und gibt ihn nicht frei.
- **Was Platypus zeigt** (platypusattack.com): Über `powercap` konnten unprivilegierte Konten
  - „break KASLR“,
  - „leak AES-NI keys from Intel SGX enclaves and the Linux kernel“,
  - RSA-Schlüssel aus Enklaven gewinnen.

  Mit SGX meldet neuer Microcode modellierte statt gemessener Energie; ohne SGX hilft das nicht.
- **Was „an“ öffnet:**
  1. `energy_uj` aller Zonen `intel-rapl:*` wird für jedes Konto lesbar. Auf Intel sind das `package-N`, `core`, `uncore`, `dram` und `psys`, auf AMD Zen die Zonen von `intel_rapl_msr`. Lesen kann sie auch jede Sandbox, die `/sys` sieht, etwa Flatpak.
  2. `intel_gpu_top` läuft für jedes Konto mit `CAP_PERFMON`. Damit liest es die PMU von i915, RAPL über perf und die Bandbreite des Speichercontrollers.
- Beide Freigaben haben dasselbe Risiko. Das stützt die Wahl eines einzigen Schalters.

## 3. Bausteine

### B2.1 Der Freigabe-Helfer

**Befund**
- Das Muster aus 0.2.0 ist tragfähig:
  - Der Helfer ist ein Python-Skript, das pkexec direkt startet: `/usr/lib/orbitop/killhelper`, 0755 root.
  - Die polkit-Action hat `auth_admin` und `exec.path`.
  - Die App prüft vor pkexec mit `_trusted` die ganze Kette bis `/`.
  - Die Argumente stehen fest, die Pfade sind absolut.
- pkexec(1):
  - Es setzt eine „minimal known and safe environment“ und `PKEXEC_UID` und startet im Home-Verzeichnis von root.
  - Es „does no validation of the ARGUMENTS“.
  - Es endet mit 126, wenn der Dialog abgebrochen wurde, und mit 127, wenn die Berechtigung fehlt, polkit „no“ sagt oder ein Fehler auftrat.
  - Laut Zweitprüfung (Quelltext `pkexec.c`) behält pkexec nur `SHELL`, `LANG`, `LC_*`, `TERM` und `COLORTERM`. `DISPLAY` und `XAUTHORITY` behält es nur mit `exec.allow_gui`. Werte mit `/`, `%` oder `..` weist es ab.
- **`exec.argv1`** wählt eine Action nur, wenn das erste Argument passt. pkexec kann das seit polkit 0.107 (NEWS, nach der Zweitprüfung); alle Ziele haben 124 bis 128 (P5).
- **`exec.path` und Pfad-Aliase:** pkexec vergleicht `exec.path` erst seit polkit 127 nach `realpath()`. Auf Ubuntu 24.04 (124) und Debian 13 (126) passt `pkexec /usr/lib/orbitop//counterhelper on` zu keiner orbitop-Action. Der Aufruf fällt dann auf `org.freedesktop.policykit.exec` zurück, also `auth_admin` in jeder Sitzung. Das ist wichtig für E2.
- **Protokoll ohne eigenen Code:** pkexec schreibt „Executing command … [COMMAND=…]“ ins Systemprotokoll, und polkitd protokolliert die Berechtigung samt Action-ID. Der Helfer muss deshalb keine Umgebung lesen, auch `PKEXEC_UID` nicht.
- **`-I` allein lädt noch `site`.** Probe P1:
  - Eine `.pth`-Datei in `/usr/lib/python3/dist-packages` lief unter `python3 -I`, unter `python3 -IS` nicht.
  - Unter `-IS` enthält `sys.path` nur die Standardbibliothek. Die `.pth`-Dateien gehören root; das ist also keine Rechteausweitung, wohl aber Fremdcode bei jedem Aufruf als root.
  - `-IS` läuft auf allen sechs Zielen (Python 3.12 bis 3.15, P5).
- **Zwei Wörter statt vier:** Die Oberfläche hat nur einen Schalter. Vier Wörter brächten zwei root-Einstiege und zwei polkit-Actions, die nie benutzt würden.
- **pkexec ist nicht überall das von polkit (I-3):**
  - Auf openSUSE Tumbleweed liefert auch `run0-wrappers` die Datei `/usr/bin/pkexec` und das Provides `pkexec`. Der Controller hat das im Container bestätigt.
  - Dieses pkexec ist ein bash-Skript, das in `run0` übergeht und keine polkit-`.policy`-Annotation beachtet.
  - Benutzer in `_run0_nopasswd` brauchen kein Passwort; wheel-Benutzer geben ihr eigenes ein.
  - `Requires: /usr/bin/pkexec` und auch `Requires: pkexec` sind damit erfüllt.

**Risiken mit Szenario**
- *R1.1: Pfad als Argument.* Nähme der Helfer einen Pfad, gäbe ein T2-Prozess nach dem Passwort `/usr/bin/python3` die Fähigkeit `cap_perfmon`. Dann hätte jedes Konto beliebiges `perf_event_open` systemweit. Abhilfe: feste Wörter, fester Pfad.
- *R1.2: TOCTOU an der Zieldatei.* Prüfen und `setcap path` sind zwei Schritte. Zwischen ihnen ließe sich ein Symlink unterschieben, wenn ein Glied des Pfads beschreibbar wäre. Abhilfe: einmal öffnen (`O_NOFOLLOW`) und alles am fd erledigen.
- *R1.3: Fremde Programme als root.* `setcap`, `chmod` und `udevadm` liegen je Distribution anders, auf Ubuntu 26.04 ist `/usr/bin/chmod` uutils (P5). Jedes fremde Programm ist zusätzlicher Code, der als root läuft. Abhilfe: Systemaufrufe aus Python.
- *R1.4: Abbruch mitten in „aus“.* Fällt der Strom nach dem Entfernen der Fähigkeit, aber bevor die Merkdatei weg ist, setzt der nächste Auslöser die Fähigkeit wieder. Abhilfe: zuerst die Merkdatei löschen, dann `fsync` auf das Verzeichnis, dann die Wirkungen zurücknehmen.
- *R1.5: Gleichzeitige Aufrufe.* `sync` läuft, während der Admin „aus“ schaltet. Ohne Lock könnte `sync` nach dem „aus“ wieder freigeben. Abhilfe: exklusives `flock`; die Merkdatei wird erst unter dem Lock gelesen.
- *R1.6: Exit-Code 126 oder 127 vom Helfer.* Die App würde ihn als „abgebrochen“ deuten. Abhilfe: Der Helfer nutzt diese Werte nie.
- *R1.7: Fremdes pkexec (I-3).* Ist `/usr/bin/pkexec` ein Ersatz wie `run0-wrappers`, startet orbitop seinen root-Helfer über einen Mechanismus, für den er nie gedacht war. Vor einem Passwort mit Risikotext und `auth_admin` schützt das dann nicht. Bei einem Benutzer ohne Passwortpflicht kann T3 die Freigabe ganz ohne Frage einschalten.
- *R1.8: Hängendes Lock.* Hielte ein anderer Prozess das Lock dauerhaft, hinge der Helfer. Pakettransaktion und App warteten dann endlos.
- *R1.9: Container.* Ein `on` in einem User-Namespace (rootless Container) schriebe eine Fähigkeit der Version 3. Sie wirkt auf dem Host nicht, und die App im Container zeigte trotzdem „an, wirkt“.

**Empfehlung (Bauweise)**
- **Datei:**
  - Im Repo `orbitop/counterhelper.py`. `install-tree.sh` installiert es als `/usr/lib/orbitop/counterhelper` (0755 root:root).
  - Nur Standardbibliothek (`os`, `sys`, `stat`, `struct`, `fcntl`, `glob`, `errno`, `time`), kein `orbitop.*`.
  - Shebang `#!/usr/bin/python3 -IS`. Für `killhelper` später gleich; das ändert sein Verhalten nicht.
- **Aufruf** `counterhelper on|off|sync`:
  - `len(sys.argv) == 2` und `sys.argv[1] in ("on", "off", "sync")`, exakt verglichen; sonst Exit 2.
  - `os.geteuid() != 0` ergibt ebenfalls Exit 2.
  - Am Anfang `os.umask(0o022)`.
  - Der Helfer liest keine Umgebungsvariablen. Ausgaben gibt es nur bei Fehlern, eine Zeile auf stderr.
- **Ablauf:**
  1. **User-Namespace:** Für `on` und `sync` muss `/proc/self/uid_map`, nach dem Zusammenfassen der Leerzeichen, genau `0 0 4294967295` sein. Sonst gibt es bei `on` Exit 3, und `sync` endet mit Exit 0, ohne etwas zu schreiben. `off` darf immer.
  2. **Verzeichnis prüfen:** `/etc/orbitop` öffnen mit `os.open(..., O_RDONLY|O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC)`.
     - Die Kette `/etc/orbitop` → `/etc` → `/` wie `_trusted` prüfen.
     - Am fd zusätzlich `fstat`: ein Verzeichnis, `st_uid == 0`, `S_IMODE & 0o022 == 0`.
     - *Ergänzung Controller 2026-11-20 (Audit Task 2, I-1):* zusätzlich kein Leserecht für Gruppe und andere, also `S_IMODE & 0o066 == 0`. Sonst könnte jedes Konto den Ordner öffnen und mit `flock` das Lock dauerhaft halten; jedes `off` endete dann nach 10 s mit Exit 1, und die Freigabe ließe sich nicht mehr zurücknehmen. Wie der Helfer einen sonst sicheren, aber lesbaren Ordner behandelt, steht in der nächsten Ergänzung. Nach Ablauf der Wartezeit läuft `off` im sicheren Fall nicht ohne Lock weiter (R1.5).
     - *Ergänzung Controller 2026-11-20 (Fix Task 2):* Ein Ordner, der alle Prüfungen besteht und nur Leserechte für Gruppe oder andere hat (`S_IMODE & 0o044`, etwa von Hand auf 0755 gesetzt), ist „schwach“: `on` ergibt 3 ohne Schreibaufruf, `sync` tut nichts (3), `off` löscht ohne Lock die Merkdatei über den fd des Ordners (`ENOENT` ist in Ordnung), ruft `fsync` darauf und nimmt dann die Wirkungen zurück, Exit `max(3, apply)`. Ohne Lock ist das sicher, weil in diesem Zustand nie ein `on` oder `sync` anwendet (R1.5). Sonst öffnete die udev-Regel RAPL beim nächsten Start wieder. Bei jedem anderen Fehler (Typ, Eigentümer, g/o-Schreibrecht, Kette, Symlink) nimmt `off` weiter nur die Wirkungen zurück.
     - Scheitert das: `on` ergibt Exit 3; `off` nimmt die Wirkungen trotzdem zurück (Schritt 5); `sync` tut nichts.
  3. **Lock:** `fcntl.flock(dirfd, LOCK_EX | LOCK_NB)` im Abstand von 0,2 s, höchstens 10 s lang, sonst Exit 1 („busy“).
  4. Je nach Wort:
     - `on`: `os.open("counters-released", O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC, 0o644, dir_fd=dirfd)`; `EEXIST` ist in Ordnung. Danach `fsync` auf Datei und Verzeichnis, dann `apply(True)`.
       - *Ergänzung Controller 2026-11-20 (Audit Task 2, M-2):* nach `EEXIST` gilt dieselbe Regel wie bei `sync`: `os.stat(..., dir_fd=dirfd, follow_symlinks=False)` muss eine reguläre Datei mit uid 0 zeigen, sonst Exit 3 ohne Wirkung.
     - `off`: `os.unlink("counters-released", dir_fd=dirfd)`; `ENOENT` ist in Ordnung. Danach `fsync(dirfd)`, dann `apply(False)`.
     - `sync`: Gibt es die Merkdatei als reguläre Datei mit uid 0 (`os.stat(..., dir_fd=dirfd, follow_symlinks=False)`), folgt `apply(True)`, **sonst nichts**. `sync` nimmt nie etwas zurück.
  5. `apply(an)` hat zwei Teile:
     - **perfmon:**
       - `/usr/bin/intel_gpu_top` öffnen mit `O_RDONLY|O_NOFOLLOW|O_CLOEXEC`. `ENOENT` ergibt „nicht vorhanden“. `ELOOP`, also ein Symlink, ergibt „nicht unterstützt“, Exit 4 und in der App „wirkt nicht“.
       - Am fd verlangen: `S_ISREG`, `st_uid == 0`, `S_IMODE & 0o022 == 0`, `st_nlink == 1`. Die Kette `/usr/bin` → `/usr` → `/` wie `_trusted`.
       - *Ergänzung Controller 2026-11-20 (Audit Task 2):* `nlink == 1` nur beim Setzen (`on`, `sync`). `removexattr` bei „aus“ senkt nur die Rechte genau des Inodes am festen Pfad; ein fremder harter Link verliert die Fähigkeit dabei mit, das schließt einen Teil von R13. `S_ISREG`, uid 0, kein g/o-Schreibrecht, `O_NOFOLLOW` und die Kettenprüfung gelten auch für „aus“: ohne sie könnte „aus“ einem anderen Paket eine nötige Fähigkeit nehmen (A5). Die Datei und die RAPL-Dateien werden zusätzlich mit `O_NONBLOCK` geöffnet, damit ein FIFO an diesem Pfad den Helfer nicht mit gehaltenem Lock blockiert (M-5).
       - Bei „an“: `os.setxattr(fd, "security.capability", CAP)`. Bei „aus“: `os.removexattr(fd, "security.capability")`, wobei `ENODATA` in Ordnung ist.
       - `CAP = struct.pack("<5I", 0x02000001, 0, 0, 1 << (38 - 32), 0)`. Das sind dieselben 20 Bytes, die `setcap cap_perfmon=ep` schreibt (P1: `0x0100000200000000000000004000000000000000`; die Zweitprüfung bestätigt das).
     - **RAPL:** für jeden Treffer von `glob("/sys/class/powercap/intel-rapl:*/energy_uj")`, also genau die Menge, die `sensors.RaplReader` liest:
       - öffnen mit `O_RDONLY|O_NOFOLLOW|O_CLOEXEC`;
       - `fstat` verlangt `S_ISREG`;
       - `m = stat.S_IMODE(st.st_mode)`;
       - bei „an“ `os.fchmod(fd, m | 0o044)`, bei „aus“ `os.fchmod(fd, m & 0o600)`.
  6. **Exit-Codes:**
     - 0: alles, was der Rechner hat, steht wie verlangt;
     - 1: unerwarteter Fehler oder Lock nicht zu bekommen;
     - 2: Aufruf ungültig oder nicht root;
     - 3: Ort oder Umgebung unsicher (Verzeichnis, Kette, User-Namespace);
     - 4: teilweise, weil ein Teil mit `OSError` scheiterte (etwa `EROFS`, `ELOOP`).

     126 und 127 kommen nie vor.
- **Was er schreiben darf**, und nur das (kein `exec`, kein Netz):
  - die Merkdatei;
  - `security.capability` an `/usr/bin/intel_gpu_top`;
  - die Bits `g+r` und `o+r` an `energy_uj` der Zonen `intel-rapl:*`.
- **polkit:** zwei Actions in der bestehenden `.policy`-Datei. Die Vorgaben stehen nach E2 = A.
  ```xml
  <action id="io.github.zappelmann-sketch.orbitop.counters-release">
    <description>Release the GPU and energy counters for all accounts</description>
    <description xml:lang="de">Grafik- und Energiezähler für alle Konten freigeben</description>
    <message>Every account on this computer will be able to read the GPU and energy counters. Risk: power side channels (Platypus, CVE-2020-8694).</message>
    <message xml:lang="de">Jedes Konto auf diesem Rechner kann dann die Grafik- und Energiezähler lesen. Risiko: Seitenkanal über den Stromverbrauch (Platypus, CVE-2020-8694).</message>
    <defaults>
      <allow_any>no</allow_any>
      <allow_inactive>no</allow_inactive>
      <allow_active>auth_admin</allow_active>
    </defaults>
    <annotate key="org.freedesktop.policykit.exec.path">/usr/lib/orbitop/counterhelper</annotate>
    <annotate key="org.freedesktop.policykit.exec.argv1">on</annotate>
  </action>
  ```
  - Dazu kommt `…orbitop.counters-lock` mit `argv1` = `off` und dem Text „Grafik- und Energiezähler wieder sperren“.
  - `sync` hat keine eigene Action. Über pkexec gilt dafür `org.freedesktop.policykit.exec` (`auth_admin`); das schadet nicht.
  - Nie `auth_admin_keep` oder `yes`, nie `org.freedesktop.policykit.exec.allow_gui`.
- **App:**
  - **pkexec-Prüfung (E5, kommt schon in Plan 1, weil sie auch 0.2.0 betrifft):** Vor jedem pkexec-Aufruf, also bei `terminate` und `counters`, verlangt die App:
    - `/usr/bin/pkexec` ist eine reguläre Datei (`lstat`, kein Symlink);
    - sie gehört root und ist nicht g/o-beschreibbar, die Kette wie bei `_trusted`;
    - `S_ISUID` ist gesetzt;
    - die ersten vier Bytes sind `\x7fELF`.

    Sonst gibt es `nohelper` mit dem Hinweis „pkexec von polkit nötig“; Schalter und „Prozess eines anderen Benutzers beenden“ sind dann nicht verfügbar. Gegen `run0-wrappers` gibt es keine Versionsbindung. `Requires: /usr/bin/pkexec` bleibt auf openSUSE und zieht auf normalen Systemen das pkexec von polkit nach.
  - **Aufruf:** eine neue Funktion in `actions.py` nach dem Muster von `terminate`.
    - Erst `_trusted("/usr/lib/orbitop/counterhelper")`, sonst `nohelper`.
    - Dann `run([PKEXEC, HELPER, "on" | "off"], timeout=120)` über `Shell._run`.
  - **Beenden:** `_shutdown` und der Timeout können pkexec beenden, solange der Dialog offen ist. Hat pkexec den Helfer gestartet, läuft dieser mit realer uid 0. `kill` scheitert dann mit `EPERM` (`PermissionError`).
    - Der counters-Thread fängt `OSError` und andere Ausnahmen wie bei `terminate` und meldet `error`.
    - `_shutdown` unterdrückt `PermissionError` und wartet nicht. Der Helfer endet von selbst: Er läuft kurz, und das Warten auf das Lock ist auf 10 s begrenzt.
  - **Ergebnis:** Was die Seite zurückbekommt, kommt aus einem frischen Lesen des Zustands (B2.5).
    - Vom Exit-Code zählt nur, ob abgebrochen (126) oder abgelehnt (127) wurde.
    - Bei 127 zeigt die App: „Nicht ausgeführt – Umschalten geht nur in einer lokalen, aktiven Sitzung und mit dem Admin-Passwort.“ Der Text passt für ein polkit-„no“ wie für einen Fehler, denn pkexec unterscheidet die beiden nicht (M-1).

**Pflicht-Tests**
- *Unit (Helfer):*
  - **Argumente:** `[]`, `["on","x"]`, `["ON"]`, `["on\n"]`, `["оn"]` (kyrillisches o) und `["--on"]` ergeben 2. Ohne root ergibt sich 2, ohne dass etwas geschrieben wird.
  - **Kettenprüfung** über gefälschtes `lstat`/`fstat`: Symlink, falscher Eigentümer, Gruppenschreibrecht oder `nlink == 2` ergeben keinen Schreibaufruf. `ELOOP` ergibt Exit 4.
  - **Modus:** Ein Modus mit Typ-Bits (`S_IFREG | 0o400`) ergibt `fchmod` mit `0o444` bzw. `0o400`, nie mit Typ-Bits. Dazu `0o600` → `0o644` → `0o600`.
  - **Reihenfolge bei `off`:** Die Merkdatei ist weg, auch wenn `removexattr` danach scheitert (Exit 4).
  - **`sync`:** Ohne Merkdatei gibt es keinen Schreibaufruf (Fake-OS-Layer). Mit Merkdatei wird alles angewendet.
  - **User-Namespace:** Bei `uid_map` `0 1000 1` gibt `on` Exit 3, und `sync` schreibt nichts.
  - **Lock:** Hält ein anderer das Lock, endet der Helfer nach 10 s mit Exit 1 (mit Uhr-Injektion).
  - **Bytes:** `CAP` ist gleich `0100000200000000000000004000000000000000`.
  - **Exit-Codes:** nie 126 oder 127.
- *Unit (App):*
  - **pkexec-Prüfung:** Ein ELF mit setuid und root ist in Ordnung. Ein Skript (`#!/bin/bash`), ein ELF ohne setuid, ein Symlink oder ein Eigentümer ≠ 0 ergeben `nohelper`, ohne Aufruf von `run`. Das gilt für `terminate` und `counters`.
  - **Exit 127:** ergibt den Grundtext. Exit 126 ergibt „abgebrochen“.
  - **`PermissionError` beim Beenden:** Er führt zu `error`, und der Gate wird wieder frei.
- *Statisch:*
  - Die erste Zeile des Helfers ist genau `#!/usr/bin/python3 -IS`.
  - Ein AST-Test zeigt: nur Standardbibliothek, kein `subprocess`, kein `os.system`, kein `os.environ`.
  - Die Policy-XML enthält zwei Actions mit `exec.path` gleich dem Installationspfad und `argv1` gleich `on` bzw. `off`.
  - Beide Actions haben `no`/`no`/`auth_admin`.
  - Nirgends `auth_admin_keep`, nirgends `yes`, **keine Annotation `org.freedesktop.policykit.exec.allow_gui`** (M-8).
  - `lint-gate.sh` (openSUSE) akzeptiert genau die drei Zeilen `polkit-untracked-privilege`: `terminate` mit `auth_admin:auth_admin:auth_admin` sowie die beiden neuen Actions mit ihren Vorgaben (`no:no:auth_admin`). Jede steht begründet in `docs/release.md` unter „Lint notes“ (M-7).
- *Container-Matrix (alle sechs Ziele, als root, ohne polkit):*
  - Nach `counterhelper on` zeigt `getcap /usr/bin/intel_gpu_top` den Wert `cap_perfmon=ep`, und die Merkdatei ist root 0644. Ein Docker mit root-Rechten läuft im Init-User-Namespace, die Prüfung lässt das also zu.
  - Nach `off` gibt es weder Fähigkeit noch Merkdatei.
  - RAPL ergibt Exit 4 ohne Absturz, weil `/sys` im Container nur lesbar ist.
- *Hardware (Testversion):*

### B2.2 Die Merkdatei

**Befund**
- `hier(7)`: `/etc` „Contains configuration files which are local to the machine“; `/var/lib` „Variable state information for programs“.
- Debian Policy 10.7:
  - 10.7.1: Konfigurationsdatei ist „A file that affects the operation of a program, or provides site- or host-specific information“.
  - 10.7.2: Sie „must reside in `/etc`“.
  - 10.7.3: „configuration files must be preserved when the package is removed, and only deleted when the package is purged“.
- Die Merkdatei steuert die udev-Regel und die Auslöser. Damit ist sie eine Konfigurationsdatei.
- **Früher Systemstart:** `systemd-udev-trigger.service` ist nur nach den udev-Sockets und vor `sysinit.target` eingereiht, nicht nach `local-fs.target` (Unit-Datei, systemd 259; die Zweitprüfung hat das bestätigt).
  - systemd verlangt `/var` erst „before the host reaches `local-fs.target`“. `/etc` muss dagegen schon beim Übergang aus der initrd da sein.
  - Ein `TEST==` auf `/var/lib/...` kann deshalb beim Start ins Leere gehen.

**Risiken mit Szenario**
- *R2.1: Fremde legt die Merkdatei an.* Das ginge nur bei einem beschreibbaren `/etc/orbitop`. Abhilfe: Das Verzeichnis gehört dem Paket (root, 0711, siehe Empfehlung), und der Helfer prüft es bei jedem Lauf.
- *R2.2: Symlink als Merkdatei.* `TEST` prüft nur, ob die Datei existiert. Einen Symlink kann nur root anlegen. Der Helfer arbeitet mit `O_NOFOLLOW` und `dir_fd`.
- *R2.3: Merkdatei überlebt die Deinstallation.* Eine Neuinstallation gäbe dann wieder frei (Anti-Ziel). Abhilfe: schon bei „remove“ löschen (E1 = A, B2.8).
- *R2.4: Löschen nicht dauerhaft.* Ohne `fsync` übersteht ein „aus“ keinen Absturz (R1.4).

**Empfehlung** (E1 = A, entschieden)
- **Merkdatei:** `/etc/orbitop/counters-released`, leer, root:root 0644.
  - Nur der Helfer legt sie an und löscht sie; dazu kommt die Sicherung in den Entfern-Skripten (B2.8).
  - Sie ist kein Conffile, kein `%config` und kein `backup=`.
  - Dass sie schon bei „remove“ verschwindet, weicht von Debian Policy 10.7.3 ab. Das steht in der Paket-Doku (`README.Debian` bzw. `docs/release.md`).
- **Verzeichnis** `/etc/orbitop/`, root:root 0711, kommt aus dem Paket, in allen vier Formaten:
  - deb: als Verzeichnis im Paketbaum, nach `dh_fixperms` wieder auf 0711 gesetzt;
  - RPM: `%dir %attr(0711,root,root) %{_sysconfdir}/orbitop`;
  - Arch: im Paket.

  *Ergänzung Controller 2026-11-20 (Audit Task 2, I-1):* ursprünglich 0755. Ein Ordner, den jedes Konto lesen kann, kann jedes Konto auch öffnen und mit `flock(LOCK_EX)` dauerhaft sperren. Der Helfer nimmt sein Lock am fd dieses Ordners; ein lokales Konto ohne Admin-Rechte könnte so jedes `off`, `on` und `sync` verhindern (im Container nachgestellt), und die Freigabe bliebe gegen den Willen des Admins an. Mit 0711 scheitert das Öffnen für andere mit `EACCES`, `lstat` der Merkdatei bleibt für jedes Konto möglich, und udev prüft `TEST` als root. Der Helfer verlangt zusätzlich, dass der Ordner für Gruppe und andere nicht lesbar ist (B2.1, Schritt 2).

  Ist es beim Entfernen leer, löscht die Paketverwaltung es selbst. Der Purge-Schritt ist eine Sicherung.
- **Lesen in der App, ohne root:**
  - `os.lstat("/etc/orbitop")`: muss ein Verzeichnis sein, mit uid 0, nicht g/o-beschreibbar und nicht g/o-lesbar (`S_IMODE & 0o066 == 0`, dieselbe Regel wie im Helfer; Ergänzung Controller 2026-11-20 (Audit Task 2, I-1)).
  - `os.lstat("/etc/orbitop/counters-released")`: muss eine reguläre Datei mit uid 0 sein.
  - Alles andere heißt „aus“ mit dem Hinweis „Zustand unklar“.
- **Format:** keine Inhalte; eine einzige Merkdatei genügt.

**Pflicht-Tests**
- *Unit (App):*
  - Ist die Merkdatei ein Symlink, ein Verzeichnis oder gehört sie nicht uid 0, ergibt das nicht „an“.
  - Ein Verzeichnis mit 0777 ergibt „unklar“.
- *Unit (Helfer):*
  - `O_EXCL` bei vorhandener Datei ist in Ordnung.
  - `fsync` auf das Verzeichnis wird aufgerufen.
- *Matrix:*
  - Die Dateiliste enthält `/etc/orbitop` als Verzeichnis 0711 und keine Merkdatei.
  - Ein anderes Konto (etwa uid 65534) kann `/etc/orbitop` nicht öffnen (`EACCES`); `off` endet mit 0, Fähigkeit und Merkdatei sind weg (Ergänzung Controller 2026-11-20 (Audit Task 2, I-1)).
  - Nach Install, Upgrade, Reinstall und jedem Auslöser gibt es keine Merkdatei, solange niemand `on` aufgerufen hat.
- *Hardware:*
  - Merkdatei an, Neustart: Die Freigabe wirkt.
  - Merkdatei aus, Neustart: Der Kernel-Standard gilt.

### B2.3 Die RAPL-Freigabe

**Befund**
- **Kernel-Standard:** `powercap_sys.c` setzt `S_IRUSR`, mit `reset_energy_uj` `S_IWUSR | S_IRUSR`.
  - Auf dem Entwicklungsrechner (Intel, Kernel 7.0) stehen alle Zonen auf 0400: `intel-rapl:0` (`package-0`), `:0:0` (`core`), `:0:1` (`uncore`), `:0:2` (`dram`), `intel-rapl:1` (`psys`), dazu `intel-rapl-mmio:0` und `:0:0`.
  - `max_energy_range_uj` und `name` stehen auf 0444.
- **AMD:** Nach der Patch-Reihe „powercap: Enable RAPL for AMD Fam17h and Fam19h“ (angekündigt für Linux 5.11; den Merge belegt keine Quelle) meldet `intel_rapl_msr` AMD Zen unter `intel-rapl:*`.
  - Welche Unterzonen AMD zeigt, ist offen. Das genügt, weil der Glob auf `intel-rapl:*` begrenzt ist; MMIO-Zonen bleiben zu.
  - *Ergänzung Controller 2026-11-20 (Audit Task 2, M-1):* Früher stand hier „MMIO- und TPMI-Zonen bleiben zu“. TPMI-Zonen (etwa Xeon 6) melden sich über `intel_rapl_tpmi` mit dem Steuertyp `intel-rapl` an, heißen also `intel-rapl:N[:M]` und gehören zur Freigabe, wie sie auch `sensors.RaplReader` liest. Geschlossen bleiben nur die Zonen `intel-rapl-mmio:*`; ein Name-Glob kann TPMI nicht ausnehmen.
- **orbitop liest nur `intel-rapl:*`** (`sensors.py`, `sampler.py`). Die Freigabe öffnet genau diese Menge.
- **udev(7):**
  - Gleichnamige Regeldateien ersetzen einander, Dateien in `/etc` haben Vorrang.
  - `MODE` gilt nur für „the device node“; für die Rechte einer sysfs-Datei braucht es deshalb `RUN`.
  - `RUN` läuft nach allen Regeln und braucht einen absoluten Pfad.
- **udevadm(8):** `--reload` wirkt nur auf neue Ereignisse. `trigger` sendet ohne `--action` ein „change“ und würde damit alle Regeln für powercap-Geräte erneut ausführen, auch fremde.
- **SELinux** (Zweitprüfung, M-2): Die mitgelieferte targeted-Policy von Fedora (selinux-policy 45.24) und openSUSE (Stand 2026-11-16) gibt `udev_t`, `rpm_script_t` und `unconfined_t` die Attribute `unconfined_domain_type`, `files_unconfined_type` und `filesystem_unconfined_type`.
  - Damit dürfen `udev RUN chmod` und `fchmod` im Helfer die Rechte von `sysfs_t` und `bin_t` ändern, und `setfcap` ist erlaubt.
  - Die Dateikontexte sind `lib_t` (Helfer, Regel), `etc_t` (Merkdatei) und `bin_t` (`intel_gpu_top`).

**Risiken mit Szenario**
- *R3.1: Verdecken.* Hieße die Paketregel `70-orbitop-rapl.rules`, ersetzte die Handregel aus der README sie. Die Handregel hat kein `TEST`, also bliebe RAPL dauernd frei.
- *R3.2: `udevadm trigger` aus dem Helfer* löste fremde Regeln erneut aus. Nötig ist es nicht.
- *R3.3: `chmod 0444` absolut* nähme ein Schreibbit weg, sodass „aus“ den alten Stand nicht herstellen kann. Abhilfe: symbolisch bzw. `& 0o600`.
- *R3.4: Zu breite Freigabe.* `intel-rapl*` würde auch die MMIO-Zonen öffnen.
- *R3.5: „aus“ trifft fremde Regeln.* „aus“ nimmt auch Leserechte zurück, die eine eigene udev-Regel eines anderen Werkzeugs vergeben hat. Das gilt bis zum nächsten Neustart oder Neuladen des Moduls (Restrisiko R16).

**Empfehlung**
- **Regeldatei** `/usr/lib/udev/rules.d/70-orbitop-counters.rules`, 0644 root (RPM: `%{_udevrulesdir}`):
  ```
  ACTION=="add", SUBSYSTEM=="powercap", KERNEL=="intel-rapl:*", TEST=="/etc/orbitop/counters-released", RUN+="/usr/bin/chmod go+r /sys%p/energy_uj"
  ```
  `/usr/bin/chmod` gibt es auf allen sechs Zielen. Die uutils-Fassung von Ubuntu 26.04 setzt `go+r` und `go-r` richtig (P5).
- **Im Betrieb** setzt der Helfer die Rechte selbst. Kein `udevadm trigger`, kein `--reload`.
- **„aus“:** `S_IMODE & 0o600`. Auf Intel ist das 0400.
- **Paket-Skripte:**
  - Fedora braucht für udev-Regeln keinen eigenen Schritt.
  - Auf openSUSE ist `%udev_rules_update` nur nötig, wenn rpmlint es verlangt.

**Pflicht-Tests**
- *Unit:*
  - Regeltest: genau eine Regel, mit `TEST` auf dieselbe Konstante wie im Helfer, `KERNEL=="intel-rapl:*"` und `go+r`.
  - Der Dateiname ist nicht `70-orbitop-rapl.rules`.
  - In einem Testbaum mit Intel-, AMD- und MMIO-Zonen ändert der Helfer nur `intel-rapl:*`.
- *Matrix:* Die Regel liegt unter `/usr/lib/udev/rules.d/`; unter `/etc/udev` liegt nichts.
- *Hardware (Pflicht):*
  - „an“ ergibt 0444; nach einem Neustart weiter 0444.
  - „aus“ ergibt 0400; nach einem Neustart weiter 0400.
  - Mit „an“ und neu geladenem `intel_rapl_msr` ergibt sich 0444. Diesen Schritt nur auf Wunsch des Users, denn er braucht `sudo`.

### B2.4 Die perfmon-Freigabe und die Paket-Auslöser

**Befund**
- **Feste Pfade und Eigentümer** (P1 bis P4, die Zweitprüfung hat sie bestätigt):

  | Ziel | Paket, dem die Datei gehört | Pfad | Art | Rechte | nlink |
  |---|---|---|---|---|---|
  | Ubuntu 24.04 | `intel-gpu-tools` 1.28 | `/usr/bin/intel_gpu_top` | ELF, regulär | 0755 root | 1 |
  | Ubuntu 26.04 | **`igt-gpu-tools`** 2.3; `intel-gpu-tools` ist ein Metapaket (`Depends: igt-gpu-tools (= 2.3-1)`) | `/usr/bin/intel_gpu_top` | regulär | 0755 root | 1 |
  | Debian 13 | `intel-gpu-tools` 2.0 | `/usr/bin/intel_gpu_top` | regulär | 0755 root | 1 |
  | Fedora 45 | `igt-gpu-tools` 2.6 | `/usr/bin/intel_gpu_top` | regulär | 0755 root | 1 |
  | openSUSE TW | **`intel-gpu-tools`** 2.5; `igt-gpu-tools` nur als Provides | `/usr/bin/intel_gpu_top` | regulär | 0755 root | 1 |
  | Arch | `intel-gpu-tools` 2.6 | `/usr/bin/intel_gpu_top` | regulär | 0755 root | 1 |

- **Die Fähigkeit geht bei jeder Neuinstallation der Datei verloren:** bei deb, bei RPM (`rpm -U --replacepkgs`) und bei pacman. Ein Update von orbitop allein berührt die Datei nicht.
- **Auslöser** (eigene Proben und Zweitprüfung):
  - **dpkg** `interest-noawait /usr/bin/intel_gpu_top`:
    - feuert bei Neuinstallation, Reinstall und Entfernen des Eigentümers, gebunden an den Pfad;
    - feuert nicht bei der Installation des interessierten Pakets selbst (dann nur `configure`).
  - **RPM:** `%filetriggerin -- /usr/bin/intel_gpu_top` feuert bei Reinstall, Upgrade und Erstinstallation des Eigentümers.
    - **`%transfiletriggerin` mit Dateipfad feuert nie** (eigene Probe; die Zweitprüfung hat es auf rpm 6.1.0 und 4.20.1 nachgestellt).
    - Mit dem Verzeichnispräfix `/usr/bin` feuert er.
  - **pacman-Hook** mit `Target = usr/bin/intel_gpu_top`: feuert bei Reinstall und Neuinstallation. Ein gleichnamiger Verweis auf `/dev/null` in `/etc/pacman.d/hooks/` schaltet ihn ab.
- **Upgrade in einer Transaktion (I-1, Zweitprüfung):** Kommen orbitop und die Intel-Werkzeuge im selben Lauf, reicht kein Datei-Auslöser bis zu orbitop:
  - **Debian 13**, alle vier Reihenfolgen (`dpkg -i A B`, `dpkg -i B A`, und im Stil von apt `--unpack` und danach `--configure --pending`): `postinst` bekommt nur `configure <alt>`, nie `triggered`.
  - **Fedora 45** (rpm 6.1.0), `rpm -U orbfake-2 igtfake-3`: gar kein `%filetriggerin`.
  - **openSUSE** (rpm 4.20.1): Dort feuerte er zufällig; darauf ist kein Verlass.
  - Die dpkg-Spec sagt dazu ausdrücklich: „When <I>'s postinst is called with ‘configure’, it must do whatever actions are necessary to deal with any trigger activations which might have occurred while it was not configured“.
  - rpm-scriptlets(7) zu `%posttrans`: „All files from the transaction have been installed or removed at this point.“
- **Kann ein Auslöser ohne Merkdatei freigeben?** Nein. Alle Paket-Skripte rufen nur `sync`, und `sync` prüft die Merkdatei unter dem Lock. In allen Formaten belegt.
- **Fähigkeit und Prozess:**
  - Der Prozess läuft im „secure-execution mode“ (ld.so(8)): `LD_PRELOAD` und Verwandte fallen weg.
  - Er ist nicht dumpable, das aufrufende Konto kann ihn also nicht mit ptrace anhängen.
  - `intel_gpu_top -o <datei>` schreibt mit den Rechten des Aufrufers.
- **`CAP_PERFMON`** (perf-security): Prozesse damit „are treated as privileged processes“ für perf. Eine Lücke in `intel_gpu_top` gibt volle perf-Rechte, aber kein root.
- **Leitlinie von dpkg:** „Trigger activation due to a particular file should not generally modify that file again.“ Die Fähigkeit auf einer fremden Datei ist die Ausnahme, die die Stufe-2-Spec zulässt. `rpm -V` meldet deshalb `........P`.

**Risiken mit Szenario**
- *R4.1: Beschreibbares Glied im Pfad.* T1 ersetzt die Datei vor dem nächsten Auslöser durch einen Symlink oder eine Kopie von `python3`, und `CAP_PERFMON` gälte für einen Interpreter. Abhilfe: Kettenprüfung, `O_NOFOLLOW`, Prüfungen am fd, `nlink == 1`.
- *R4.2: Paket einer Drittquelle* an diesem Pfad bekäme die Fähigkeit (Restrisiko R3).
- *R4.3: Lock fehlt.* Ein „aus“ während eines apt-Laufs; danach setzte `sync` die Fähigkeit wieder (R1.5).
- *R4.4: `%transfiletriggerin` mit Dateipfad feuert nie.* Die Freigabe ginge nach jedem Update still verloren.
- *R4.5: Upgrade in einer Transaktion (I-1).* Kommt der übliche Stapel von Updates mit orbitop und den Intel-Werkzeugen zusammen, verliert die neue Datei die Fähigkeit, und nichts setzt sie wieder. Aus „an“ wird „an, wirkt nicht“ bis zum nächsten Update der Werkzeuge. Das schließt sicher, bricht aber die Regel „an gilt für den Rechner“.
- *R4.6: Harte Links* (M-4). Mit `fs.protected_hardlinks=0` kann ein Benutzer das `intel_gpu_top` mit Fähigkeit in ein eigenes Verzeichnis verlinken. Der Inode bleibt dann über Updates und über „aus“ hinaus bestehen, und `off` findet solche Links nicht. systemd setzt den Wert auf allen Zielen auf 1, und `nlink == 1` vor dem Setzen hält schon vorhandene Links ab (Restrisiko R13).

**Empfehlung**
- **Debian/Ubuntu:**
  - `debian/orbitop.triggers`: `interest-noawait /usr/bin/intel_gpu_top`.
  - `debian/orbitop.postinst`:
    ```sh
    case "$1" in
        configure|triggered) /usr/lib/orbitop/counterhelper sync || echo "orbitop: counter release not applied" >&2 ;;
    esac
    ```
- **RPM (Fedora, openSUSE):**
  ```
  %filetriggerin -- /usr/bin/intel_gpu_top
  /usr/lib/orbitop/counterhelper sync || :

  %posttrans
  /usr/lib/orbitop/counterhelper sync || :
  ```
  - Dazu `Requires: /usr/bin/pkexec`. Auf openSUSE ist pkexec ein eigenes Paket, das `polkit` nicht nachzieht; zu `run0-wrappers` siehe B2.1 und E5.
  - Für `setcap` braucht es keine Abhängigkeit. Die Zeile `libcap2-bin`/`libcap`/`libcap-progs` fällt aus der Stufe-2-Tabelle weg.
- **Arch:** `/usr/share/libalpm/hooks/orbitop-counters.hook`
  ```
  [Trigger]
  Type = Path
  Operation = Install
  Operation = Upgrade
  Target = usr/bin/intel_gpu_top

  [Action]
  Description = Applying the orbitop counter release, if turned on...
  When = PostTransaction
  Exec = /usr/lib/orbitop/counterhelper sync
  ```
  Der `PostTransaction`-Hook deckt auch das gemeinsame Upgrade ab; der Test dazu kommt trotzdem.
- **Pfad:** Die Fähigkeit liegt nur auf diesem Pfad. Für die Grafik-Zähler startet die App `/usr/bin/intel_gpu_top` (B2.5).

**Pflicht-Tests**
- *Unit (Grep über `packaging/`):*
  - `counterhelper sync` steht nur in `postinst` (Zweig `configure|triggered`), in `%filetriggerin`, in `%posttrans` und im Hook.
  - `counterhelper off` steht nur in den Entfern-Skripten.
  - `on` kommt nirgends vor.
- *Container-Matrix, je Ziel:*
  1. Reinstall des Eigentümers ohne Merkdatei: keine Fähigkeit.
  2. `on`, dann Reinstall: Fähigkeit da.
  3. Eigentümer entfernen: Der Helfer endet mit 0.
  4. Erstinstallation der Intel-Werkzeuge nach `on`: Fähigkeit da.
  5. Erstinstallation von orbitop bei Fähigkeit von Hand: keine Merkdatei, Fähigkeit unverändert.
  6. **Neu (I-1), je Format:**
     - Merkdatei an; orbitop und das Intel-Paket in **einer** Transaktion auf die nächste Version heben. Danach ist die Fähigkeit da.
     - deb: `apt-get install ./orbitop_N+1.deb ./igt_N+1.deb` sowie `dpkg -i` in beiden Reihenfolgen.
     - RPM: `rpm -U orbitop igt` bzw. `dnf upgrade` / `zypper up`.
     - Arch: `pacman -U` mit beiden Paketen.
  7. RPM: `rpm -V` meldet nach `on` ein `P`; das kommt in den Matrix-Bericht.
  8. Auf Fedora und openSUSE: `rpm -q --whatprovides /usr/bin/pkexec` liefert `pkexec` bzw. `polkit`, nicht `run0-wrappers`.
- *Hardware:* Nach `on` und `sudo apt install --reinstall igt-gpu-tools` (Ubuntu 26.04) ist die Fähigkeit wieder da.

### B2.5 Zustand ohne root

**Befund**
- xattr(7): Ohne Sicherheitsmodul dürfen alle Prozesse `security.capability` lesen.
- capabilities(7): v2 hat 20 Bytes, v3 hat 24 Bytes mit `rootid`.
  - Laut Zweitprüfung liefert der Kernel einem Leser im Init-Namespace nie v3 mit `rootid` 0.
  - Ein v3 mit einer anderen `rootid` wirkt dort nicht.
- **Fehler in 0.2.0:** `gpu_tools._has_capability` liefert `True` bei irgendeiner Fähigkeit, und ebenso bei euid 0.
- **Fehler in 0.2.0:** `TOOL_PATH` sucht zuerst in `/usr/local/bin`.
- Rechte unter sysfs und die Merkdatei kann nur root ändern.

**Risiken mit Szenario**
- *R5.1: Falsches „an“* durch eine fremde Fähigkeit.
- *R5.2: T2 fälscht die eigene Anzeige* über ptrace oder einen eigenen Mount-Namespace. Das überschreitet keine Grenze.

**Empfehlung**
- **Parser** `perfmon_cap(path)`, über `os.getxattr(path, "security.capability", follow_symlinks=False)`:
  - Länge 20 mit Revision `0x02000000`, oder Länge 24 mit Revision `0x03000000` und `rootid == 0`;
  - das Effective-Bit ist gesetzt;
  - Bit 38 steht im 64-Bit-Permitted-Set;
  - alles andere ist `False`.

  Für „von Hand“ zählt zusätzlich Bit 21 (`CAP_SYS_ADMIN`).
- **Zustand je Teil:**

  | Merkdatei | Wirkung | Anzeige |
  |---|---|---|
  | ja | Fähigkeit am festen Pfad bzw. alle Zonen `o+r` | an, „wirkt“ |
  | ja | Werkzeug oder Zonen fehlen | an, „`intel_gpu_top` ist nicht installiert“ bzw. „keine Energiezähler“ |
  | ja | Werkzeug da, Fähigkeit fehlt, Pfad ist ein Symlink (`ELOOP`) oder Zonen nicht lesbar | an, „wirkt nicht – Schalter aus- und einschalten“ |
  | nein | Wirkung da | aus, „von Hand freigegeben“ (B2.9) |
  | nein | keine Wirkung | aus |

  Der Schalter zeigt nur die Merkdatei. Ist `/usr/bin/pkexec` nicht das von polkit, ist er gesperrt und zeigt „pkexec von polkit nötig“ (E5).
- **Ausführen:** Gibt es `/usr/bin/intel_gpu_top`, nimmt die App diesen Pfad. `/usr/local/bin` dient nur als Rückfall.
- **Vertrauen:** Aus dem Zustand folgen nur die Anzeige und die Vorbedingungen. Was zählt, entscheidet der Helfer als root.

**Pflicht-Tests**
- *Unit:*
  - **Parser-Fixtures:**
    - v2 perfmon: `True`.
    - v2 `cap_net_raw`: `False`.
    - v2 ohne Effective-Bit: `False`.
    - v3 mit `rootid` 1000: `False`.
    - v3 mit `rootid` 0: `True`.
    - Abgeschnittene oder überlange Bytes: `False`.
    - `ENODATA` oder `ENOTSUP`: `False`.
  - Zustandstabelle über einen Testbaum, einschließlich `ELOOP`.
  - Vorrang in `TOOL_PATH`.
- *Hardware:* alle Zeilen der Tabelle.

### B2.6 Der Knopf „Installieren“ über PackageKit

**Befund**
- **D-Bus:**
  - `CreateTransaction()` liefert einen Objektpfad.
  - Darauf folgt `Resolve(t filter, as names)`, das `Package(u info, s package_id, s summary)` und `Finished` sendet.
  - Danach braucht es eine neue Transaktion mit `InstallPackages(t transaction_flags, as package_ids)`. Diese darf laut Doku auch „removing“ melden.
- **polkit in PackageKit** (`pk-transaction.c` 1.3.1):
  - Ohne `ONLY_TRUSTED` gilt `…package-install-untrusted`, mit ihm `…package-install`.
  - `SIMULATE` braucht keine Berechtigung.
  - Nach einer Berechtigung wird nur mit `interactive=true` gefragt.
- **Werte** (1.3.1 = 1.4.0):

  | Art | Werte |
  |---|---|
  | Flags | `ONLY_TRUSTED = 2`, `SIMULATE = 4` |
  | Filter | `NOT_INSTALLED = 1<<3`, `NEWEST = 1<<16`, `ARCH = 1<<18` |
  | Info | `UPDATING = 11`, `INSTALLING = 12`, `REMOVING = 13`, `OBSOLETING = 15`, `REINSTALLING = 19`, `DOWNGRADING = 20` |

  Auf `main` sind diese Werte umsortiert. Die Zweitprüfung hat das bestätigt; deshalb das Tor `VersionMajor == 1`.
- **Probe P6** (Debian 13, PackageKit 1.3.1, Gio):
  - `Resolve` findet genau `intel-gpu-tools;2.0-1;amd64;…`; unbekannte Namen bleiben still.
  - Die Simulation meldet nur 12.
  - Die echte Installation meldet 10 und 18 und installiert.
- **polkit-Vorgaben je Distribution** (eigene Proben P7, P9 und Zweitprüfung):

  | Ziel | PackageKit | `package-install` (any/inactive/active) | `-untrusted` | Regel `org.freedesktop.packagekit.rules` |
  |---|---|---|---|---|
  | Ubuntu 24.04 | 1.2.8 | auth_admin / auth_admin / auth_admin_keep | auth_admin ×3 | `yes` nur für `upgrade-system`, `trigger-offline-update` |
  | Ubuntu 26.04 | 1.3.4 | wie oben | wie oben | `yes` nur für `system-update`, `trigger-offline-update`, `trigger-offline-upgrade`; `policykit-desktop-privileges` hat keine PackageKit-Action |
  | Debian 13 | 1.3.1 | wie oben | wie oben | wie Ubuntu 24.04 |
  | **Fedora 45** | 1.4.0 | wie oben | wie oben | **`yes` auch für `package-install` und `package-remove`** (zusätzlich `system-update`, `upgrade-system`, `trigger-offline-update`, `trigger-offline-upgrade`) |
  | openSUSE TW | 1.4.0 | auth_admin_keep ×3 (`polkit-default-privs`) | auth_admin ×3 | keine; `90-default-privs.rules` |
  | Arch | 1.4.0 (extra) | wie Ubuntu | wie Ubuntu | wie upstream: `yes` nur für `system-update`, `trigger-offline-update`, `trigger-offline-upgrade` |

  Wo `yes` steht, gilt es immer nur für `subject.active == true && subject.local == true && (isInGroup("wheel") || isInGroup("sudo"))`.

  **Korrektur zur Spec:**
  - Auf Ubuntu ist die Regel die von PackageKit selbst, und sie gilt nur für Updates.
  - **Auf Fedora** liefert das Paket `PackageKit-1.4.0-3.fc45` eine eigene Fassung der Regel. Damit installiert ein aktiver lokaler wheel/sudo-Benutzer **ohne Passwort** (I-2; vom Controller und selbst im Container geprüft).
  - Sonst gilt `auth_admin_keep`, also eine Erlaubnis „for a brief period (e.g. five minutes)“ für den Prozess orbitop.
  - orbitop ändert keine dieser Regeln (Anti-Ziel).
- **Ist PackageKit vorhanden?**
  - Ubuntu 26.04 Desktop: ja.
  - Debian: hängt vom Desktop ab.
  - Fedora 45: liegt im Archiv; ob Workstation es mitbringt, prüft der Builder.
  - openSUSE TW: liegt im Archiv.
  - Arch: nicht vorinstalliert.

  → „Befehl zeigen“ ist ein gleichwertiger Weg.
- **Paketnamen** (P1 bis P4; M-12):
  - apt: erst `igt-gpu-tools` (Ubuntu 26.04 und Nachfolger), sonst `intel-gpu-tools` (Ubuntu 24.04, Debian 13; auf 26.04 ein Metapaket, das noch funktioniert);
  - dnf: `igt-gpu-tools`;
  - zypper: `intel-gpu-tools`;
  - pacman: `intel-gpu-tools`.

**Risiken mit Szenario**
- *R6.1: Unsigniertes Paket.* Ohne `ONLY_TRUSTED` wäre auch ein Paket ohne Signatur möglich.
- *R6.2: Abhängigkeiten.* Eine Konfliktauflösung entfernt Pakete, ohne zu fragen.
- *R6.3: Rückfragen.* `RepoSignatureRequired` oder `EulaRequired` anzunehmen hieße, einen neuen Schlüssel einzubinden.
- *R6.4: Installation durch die Seite.*

  - Eine neue Grenze überschreitet das nicht: Der Name ist fest, `ONLY_TRUSTED` gilt, das Paket kommt aus der Distribution, und die Regel gehört ihr. Einzige Grenze ist die harte Vorbedingung in Python: einmal je Sitzung und nur, solange `hint.igt_missing` aktiv ist.
  - **Andere Distributionen:** Innerhalb der fünf Minuten von `auth_admin_keep` passiert wegen des festen Namens und ohne `ALLOW_REINSTALL` nichts weiter.
- *R6.5: Andere Kodierung* bei PackageKit 2.x.
- *R6.6: Zeitfenster zwischen Simulation und Installation.* Die Paket-IDs legen Version und Quelle fest. Eine Auffrischung des Caches dazwischen könnte aber die Abhängigkeiten ändern. Das Fenster ist klein, und die Pakete sind signiert (Restrisiko R15).

**Empfehlung**

5. Eine neue Transaktion: `SetHints(["interactive=true"])`, dann `InstallPackages(ONLY_TRUSTED, [id])`.

   - Kein zweiter Versuch ohne `ONLY_TRUSTED`.
   - **Der Ablauf setzt keinen Dialog voraus.** Auf Fedora endet er ohne Dialog in `installed`.
6. Der Ablauf läuft asynchron; der Knopf ist dabei gesperrt. Beim Beenden ruft die App `Cancel`.
7. **Harte Vorbedingung (B2.7):** Es gibt Intel-Grafik, `hint.igt_missing` ist aktiv, und in dieser Sitzung gab es noch keinen erfolgreichen Auftrag. Auf Fedora ist das die einzige Grenze.

### B2.7 Die Seite als Angreifer

**Befund**
- `parse_message` ist die einzige Schleuse. Der Zweig `autostart` übernimmt nur das normalisierte Feld und lässt alle anderen fallen.
- `Shell._terminating` lässt einen Auftrag gleichzeitig zu, kennt aber keine Sperre.
- Die WebView ist gehärtet. Eine Kompromittierung setzt eine Lücke in WebKit voraus.

**Risiken mit Szenario**
- *R7.1: Dialogschleife* bis zur Zermürbung: Der Benutzer gibt schließlich das Passwort ein, damit es aufhört.
- *R7.2: Phishing:* Die Seite zeigt falschen Text, polkit zeigt die echte Action. Diesen Dialog kann die Seite nicht fälschen.
- *R7.3: Installation:* Auf Fedora geht einmal je Sitzung eine Installation ohne Dialog (R6.4). Sonst ist eine Wiederholung harmlos.
- *R7.4: Mehrere Dialoge zugleich.*

**Empfehlung**
- **Nachrichten:** `{"type":"counters","on":true|false}` und `{"type":"install_tool"}`.
  - **Regel (M-9):** wie bei `autostart`. Zusatzfelder werden ignoriert, nur normalisierte Felder verlassen `parse_message`. Ein falscher Typ (`on` ist nicht `bool`) ergibt `None`.
- **Ein Tor** für `terminate`, `counters` und `install_tool`. Ein zweiter Auftrag bekommt `busy`.
- **Wachsende Sperre (M-10)** für `counters` und `install_tool`, nach jedem `denied` oder Abbruch (pkexec 126/127, PackageKit nicht berechtigt bzw. abgebrochen):
  - nach der ersten Ablehnung 10 s;
  - nach der zweiten 60 s;
  - nach der dritten gesperrt bis zum Neustart von orbitop, mit dem Hinweis „zu oft abgelehnt – orbitop neu starten“.

  Ein Erfolg setzt den Zähler zurück. Bei `terminate` bleibt alles wie in 0.2.0.
- **Vorbedingungen in Python:**
  - `counters`: Der gewünschte Zustand weicht von der Merkdatei ab, der Helfer ist `_trusted`, und pkexec ist das von polkit (E5).
  - `install_tool`: Es gibt Intel-Grafik, `hint.igt_missing` ist aktiv, und es gab noch keinen Erfolg in dieser Sitzung.
- Der **Text im polkit-Dialog** nennt Wirkung und Risiko. Für orbitops eigene Actions gibt es nie `auth_admin_keep`.
- **Erklärung in der Seite (E6):** Die Erklärung und der Schritt „Freigeben“ vor polkit bleiben wie in C1. Sie helfen bei der Bedienung, sind aber **kein Schutz**, denn T3 kann sie überspringen. Den Schutz leisten polkit und der Text der Action.
- **Antworten** sind nur feste Wörter.
- *Verworfen:*
  - ein eigener GTK-Dialog;
  - eine Prüfung „nur nach Klick“ in Python.

**Pflicht-Tests**
- *Unit:*
  - `parse_message`: Bei `{"type":"counters","on":true,"x":1}` kommt genau `{"type":"counters","on":true}` heraus. `on` als `1`, `"true"` oder `null` ergibt `None`. Bei `install_tool` mit `package` fällt `package` weg.
  - Tor: Zwei Aufträge ergeben einmal `run` und einmal `busy`.
  - Sperre mit Uhr-Injektion: 126 ergibt 10 s `busy`; noch einmal 126 ergibt 60 s; das dritte Mal ergibt gesperrt bis zum Neustart; ein Erfolg dazwischen setzt zurück.
  - `counters on` bei vorhandener Merkdatei ergibt keinen Aufruf von `run`.
  - Exit 127 ergibt den Grundtext aus B2.1 (M-1).
- *Chrome-Prüfseite:*
  - Es werden nur diese Formen gesendet.
  - Der Knopf ist während des Auftrags gesperrt.
  - Erklärung und „Freigeben“ stehen vor dem Senden.
- *Hardware:* Zehnmal `counters` aus der Konsole ergibt einen Dialog. Danach greift die Sperre wie oben.

### B2.8 Deinstallation, Purge und Upgrade-Pfade

**Befund**
- **Debian Policy 6.5/6.8:**
  - Beim Entfernen läuft `prerm remove`, dann werden die Dateien entfernt, dann `postrm remove`; bei einem Purge folgt `postrm purge`.
  - Bei einem Upgrade läuft `old-prerm upgrade`.
- **rpm-scriptlets(7):** `$1 == 0` heißt endgültig entfernt. Ein `%preun` mit Exit ≠ 0 verhindert die Entfernung.
- **pacman/Arch:** `.install` mit `pre_remove`/`post_remove`. pacman und RPM kennen kein Purge.
- **0.2.0** kennt keine Merkdatei.

**Empfehlung**

| Format | Entfernen | Purge / endgültig | Install, Upgrade, Reinstall |
|---|---|---|---|
| deb | `prerm`: `remove) /usr/lib/orbitop/counterhelper off \|\| echo … >&2 ;;` · `postrm`: `remove) rm -f /etc/orbitop/counters-released ;;` | `postrm`: `purge) rm -f /etc/orbitop/counters-released; rmdir /etc/orbitop 2>/dev/null \|\| true ;;` | `postinst configure` ruft `sync` (B2.4) |
| RPM | `%preun`: `if [ "$1" -eq 0 ]; then /usr/lib/orbitop/counterhelper off \|\| :; fi` | `%postun`: `if [ "$1" -eq 0 ]; then rm -f …; rmdir /etc/orbitop 2>/dev/null \|\| :; fi` | `%posttrans` ruft `sync` |
| Arch | `pre_remove() { /usr/lib/orbitop/counterhelper off \|\| true; }` | `post_remove() { rm -f …; rmdir /etc/orbitop 2>/dev/null \|\| true; }` | der Hook deckt die Intel-Werkzeuge ab; `post_upgrade` bleibt beim Schlüssel |

- **Upgrade ruft `sync`, und `sync` tut ohne Merkdatei nichts.**
  - Eine Erstinstallation und das Upgrade von 0.2.0 auf 0.3.0 bleiben wirkungslos.
  - `0.3.0~rc1` → `0.3.0` stellt bei „an“ die Fähigkeit sicher her.
- `off` nimmt auch eine von Hand gesetzte Fähigkeit am festen Pfad zurück. Die README sagt das unter „Uninstall“.
- Kein Skript scheitert wegen des Helfers.
- **Defekter Helfer beim Entfernen (M-3):** Läuft `off` nicht, löscht die Sicherung die Merkdatei trotzdem. Die Fähigkeit auf `intel_gpu_top` bleibt aber, und RAPL steht bis zum Neustart auf 0444.
  - Die README nennt für diesen Fall `sudo setcap -r /usr/bin/intel_gpu_top` und den Neustart.
  - libcap kommt dafür nicht als Abhängigkeit zurück (Restrisiko R14).
- **Testversion (E7):**
  - Nur als `.deb`, denn dpkg sortiert `0.3.0~rc1` vor `0.3.0`.
  - pacman sortiert `~rc1` nach `0.3.0` (`vercmp` = 1, Zweitprüfung) und würde das Update blockieren.
  - RPM sortiert richtig, wird aber nicht gebaut.
  - Die Spec-Aussage „in allen vier Formaten“ ist damit gegenstandslos.
- **Downgrade** auf 0.2.0: Die Merkdatei bleibt. Die README sagt: „vor einem Downgrade den Schalter ausschalten“ (Restrisiko R7).

**Pflicht-Tests**
- *Container-Matrix, je Format:*
  1. `on`, dann entfernen: keine Merkdatei, keine Fähigkeit und kein `/etc/orbitop` (deb spätestens nach Purge).
  2. Neu installieren und die Intel-Werkzeuge neu installieren: keine Fähigkeit.
  3. 0.2.0 → 0.3.0: keine Merkdatei, keine Fähigkeit. Eine Fähigkeit von Hand bleibt.
  4. 0.3.0 → 0.3.0-2 bei „an“: Merkdatei und Fähigkeit bleiben.
  5. Das gemeinsame Upgrade aus B2.4, Fall 6.
  6. **Entfernen bei defektem Helfer** (`chmod -x` im Container): Das Entfernen gelingt und die Merkdatei ist weg. Der Test **erwartet**, dass die Fähigkeit bleibt (M-3), und der Matrix-Bericht nennt das.
  7. deb mit `apt purge`: Unter `/etc/orbitop` bleibt nichts.
- *Hardware:* `rc1` → `rc2` → `0.3.0`, alle als `.deb`, mit „an“: Die Freigabe bleibt, ohne Dialog.

### B2.9 Von Hand gesetzte Freigaben (README 0.2.0)

**Befund**
- Die README von 0.2.0 nennt `setcap cap_perfmon=ep` und die Regel `/etc/udev/rules.d/70-orbitop-rapl.rules` (`chmod 0444`).
- Der Name der Paketregel ist anders. Beide Regeln wirken nebeneinander, keine verdeckt die andere.

**Risiken mit Szenario**
- *R9.1: Die Freigabe kehrt beim Start zurück.* Die Handregel gibt RAPL nach „aus“ beim nächsten Start wieder frei.
- *R9.2: Fremde Dateien löschen.* Das ist verboten.

**Empfehlung**
- **Erkennen nach der Wirkung:** keine Merkdatei, aber eine Wirkung, ergibt „von Hand freigegeben“. Mit `os.path.lexists` auf den README-Namen nennt der Hinweis den Umstieg genau.
- **„aus“:**
  - Die Fähigkeit am festen Pfad fällt weg, auch eine von Hand gesetzte.
  - `go-r` gilt sofort.
  - Die Handregel bleibt.
  - Der Hinweis sagt: „Energiezähler: eine eigene udev-Regel gibt sie beim Start frei – siehe README“.
  - „aus“ nimmt auch Rechte zurück, die Regeln anderer Werkzeuge vergeben haben, bis zum Neustart (R16).
- **Bedienung:** Der Schalter steht auf „aus“. Die Fähigkeit von Hand verschwindet über „an“ und „aus“ (Teil D0) oder über die README.
- **README (C6):**
  ```sh
  sudo rm -f /etc/udev/rules.d/70-orbitop-rapl.rules
  sudo setcap -r /usr/bin/intel_gpu_top
  ```
  Danach den Schalter einschalten.

**Pflicht-Tests**
- *Unit:*
  - Handregel ohne Merkdatei und 0444 ergibt „von Hand“.
  - Mit Merkdatei ergibt es „an“, und der Hinweis bleibt.
  - `off` löscht nichts unter `etc/udev`.
- *Matrix:* Eine Handregel ist nach Installieren und Entfernen unverändert.
- *Hardware:*
  - Fähigkeit von Hand ergibt „von Hand“.
  - `on` und dann `off` ergeben keine Fähigkeit.

## 4. Entscheidungen für den User (entschieden)

Alle Punkte sind **entschieden vom Controller im Auftrag des Users, 2026-11-19**. Der User hat ihm an diesem Tag alle Entscheidungen übertragen.

**E1: Ort und Löschzeitpunkt der Merkdatei. Entscheidung: A.**
- Die Merkdatei ist `/etc/orbitop/counters-released` und wird schon bei „remove“ gelöscht.
- Das ist eine dokumentierte Abweichung von Debian Policy 10.7.3 („must be preserved when the package is removed“). Sie gründet auf dem Anti-Ziel, dass eine Neuinstallation nichts freigibt.
- Für RPM und Arch gibt es den Konflikt nicht.
- Verworfene Wege:
  - B, `/var/lib`: udev wartet beim Start nicht auf `/var`; eine eigene systemd-Unit wäre nötig.
  - C, Löschen erst beim Purge: Eine Neuinstallation gäbe wieder frei.
  - D aus der Zweitprüfung, Löschen in `preinst install <alt>`: hebelt 10.7.3 ebenso aus und braucht einen weiteren Skriptweg.

**E2: Nur lokale, aktive Sitzungen. Entscheidung: A.**
- Die neuen Actions bekommen `allow_any=no`, `allow_inactive=no` und `allow_active=auth_admin`.
- **Begründung (nach M-1):** E2 verhindert nur, dass orbitops eigener Dialog in einer entfernten oder inaktiven Sitzung erscheint.
  - Gegen jemanden mit Admin-Passwort ist das keine Schranke. Er hat ohnehin root.
  - Auf polkit < 127 (Ubuntu 24.04, Debian 13) führt ein Pfad-Alias zur allgemeinen Action `org.freedesktop.policykit.exec` mit `auth_admin`.
- polkit „no“ lässt pkexec ohne Dialog mit 127 enden. Die App zeigt dann „Nicht ausgeführt – Umschalten geht nur in einer lokalen, aktiven Sitzung und mit dem Admin-Passwort.“ Der Text passt für „no“ wie für einen Fehler.
- Die README nennt für entfernte Sitzungen `sudo /usr/lib/orbitop/counterhelper on|off`.

**E3: Stille Installation auf Fedora (I-2). Entscheidung:**
- orbitop ändert die Regel der Distribution nicht.
- Die harte Vorbedingung in Python bleibt: einmal je Sitzung und nur, solange `hint.igt_missing` aktiv ist. Auf Fedora ist sie die einzige Grenze.
- Der Ablauf setzt keinen Dialog voraus; ein Test mit Fake-Bus belegt das.
- Die README sagt: „auf Fedora ohne Passwortabfrage (Regel der Distribution)“.

**E4: Upgrade wendet die Freigabe neu an (I-1). Entscheidung:**
- Übernommen: `sync` auch in `postinst configure|triggered` (deb) und in `%posttrans` (RPM). `%filetriggerin` bleibt.
- Für pacman reicht der Hook.
- Für jedes Format gibt es einen neuen Matrix-Fall.
- Für den Benutzer ändert sich nichts Sichtbares.

**E5: pkexec, das nicht von polkit ist (I-3). Entscheidung:**
- Vor jedem pkexec-Aufruf (`terminate` und `counters`) verlangt die App: `/usr/bin/pkexec` ist eine reguläre, root-eigene Datei mit `S_ISUID`, die mit `\x7fELF` beginnt.
- Sonst gilt `nohelper` mit dem Hinweis „pkexec von polkit nötig“. Diese Prüfung entsteht schon in Plan 1, weil sie 0.2.0 betrifft.
- Es gibt keine Versionsbindung gegen `run0-wrappers`. `Requires: /usr/bin/pkexec` bleibt auf openSUSE.

**E6: Erklärung in der Seite. Entscheidung:**
- Die Erklärung und der Schritt „Freigeben“ vor polkit bleiben, wie C1 sie beschreibt.
- Sie dienen der Bedienung und sind kein Schutz.

**E7: Testversion. Entscheidung:**
- Die Testversion wird nur als `.deb` gebaut. dpkg sortiert `~rc1` vor `0.3.0`, pacman nicht.
